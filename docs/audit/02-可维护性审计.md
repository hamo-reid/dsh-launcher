# DSH Launcher 可维护性审计报告

**结论一句话**：分层与类型健康是亮点（core 纯净、shared 契约单一、全库几乎零 `any`、core 测试扎实），但**横切样板重复**（IPC try/catch ×45+、错误处理 ×67、`majorOf` ×6、`StepIcon`/`upsert` ×3）与**契约漂移点**（渲染层重定义 shared 类型、preload 内联匿名类型）是需要优先治理的债务，且**渲染层几乎无测试**。

---

## 🔴 高严重度

### H1. IPC 层每个 handler 的 try/catch 样板重复（约 45 处），遗漏即崩溃
- **文件:行号**：`src/main/ipc/profile.ts`（25 个 handler）、`src/main/ipc/dsh.ts`（20 个 handler）
- **证据**：几乎每个 handler 都是同一骨架：
  ```ts
  // ipc/profile.ts:89-95
  ipcMain.handle('profile:list', (): IpcResult<string[]> => {
    try {
      return { ok: true, value: listProfiles() }
    } catch (error) {
      return failFromError(error)
    }
  })
  ```
  （`dsh.ts` 同款，如 `dsh:setActive` 222-233、`dsh:rename` 268-279……共 45+ 处）
- **影响**：新增 handler 必须手动粘贴 try/catch；一旦遗漏，未捕获异常会直接打穿 IPC 层。属"复制粘贴型"最高频样板。
- **建议**：抽 `wrap<T>(fn: () => T | Promise<T>): IpcResult<T>`（async-aware），或 `handle(channel, fn)` 封装 `ipcMain.handle` + 自动 `failFromError`。可一举删掉 40+ 行样板。

### H2. 渲染层重复定义 shared 契约类型（两份本地拷贝）
- **文件:行号**：
  - `src/renderer/src/views/ProfileSection.tsx:23-28` 本地重定义 `ProfileSummary`
  - `src/renderer/src/views/DshSection.tsx:17-32` 本地重定义 `DshEntry`
  - 正源：`src/shared/types.ts:284`（ProfileSummary）、`:121-142`（DshEntry）
- **证据**：`ProfileSection.tsx:23` 与 `shared/types.ts:284` 字段逐字相同；`DshSection.tsx:17` 拷贝 `DshEntry` 但**已缺字段**（无 `versionDir`，`managed` 注释也简化了）。因结构化类型兼容，`window.api` 返回的 shared 类型可直接赋给本地类型而不报错，冗余被掩盖。
- **影响**：shared 契约演进时，本地拷贝是漂移温床——DshEntry 新增字段，视图层读不到；两处要同步维护。
- **建议**：直接 `import type { DshEntry, ProfileSummary } from '../../../shared/types.ts'`，删除本地 interface。

### H3. `src/main/core/plugins.ts` 899 行，单文件职责过载（全库最大核心文件）
- **文件:行号**：`src/main/core/plugins.ts`（共 899 行）
- **证据**：一个文件承载了 store 布局、legacy 迁移、来源追踪、下载/归档、本地添加、README、scope 枚举、overview 构建、级联卸载、`deleteTreePhysical` 全部职责。其中 `migrateLegacyStore` 73 行（253-325）、`buildInstalledOverview` 80 行（748-830）、`removePluginFromProfiles` 52 行（494-546）。
- **影响**：任何 store 改动都落进同一文件；对应测试 `plugins.test.ts` 也已 546 行，导航成本高。
- **建议**：按职责拆分为 `store-layout.ts`（archive 布局/版本枚举）、`migration.ts`、`install.ts`（installSource/installIntoProfile）、`overview.ts`、`uninstall.ts`。

## 🟡 中严重度

### M1. `majorOf`（解析版本主号）全库复制 6 份，语义还不同
- **文件:行号**：`src/renderer/src/views/DshModals.tsx:530`、`DshSection.tsx:160`、`ProfileModals.tsx:170`；`src/main/core/home-data.ts:154`、`profile.ts:236`；正源在 `src/main/core/version.ts:45`（`majorOfVersion`，已导出）。
- **证据**：
  ```ts
  // DshModals.tsx:530 返回 null
  function majorOf(version: string): number | null { ... }
  // ProfileModals.tsx:170 返回 -1（哨兵值不同！）
  const majorOf = (v: string): number => { ... return -1 }
  ```
- **影响**：同一概念三种行为（null / -1 / 数字），渲染层三份、core 两份、`version.ts` 一份；改一个漏一个。
- **建议**：渲染层统一 import `majorOfVersion`（core 导出），删掉三份本地实现。

### M2. 进度条 UI 三件套跨文件复制（StepIcon / upsert / 失败详情弹窗）
- **文件:行号**：
  - `StepIcon`（完全相同）：`DshModals.tsx:168-172` == `ProfileModals.tsx:106-110`
  - `upsert`（完全相同）：`DshModals.tsx:198-205`、`ProfileModals.tsx:125-132`、`ProfileModals.tsx:322-329`（同一文件内两份）
  - "失败详情"复制/关闭弹窗（完全相同）：`DshModals.tsx:376-387` == `ProfileModals.tsx:282-293`
  - dist-tags 标签行（近似）：`DshModals.tsx:307-311` ≈ `PluginsModals.tsx:323-329`
  - 版本列表加载 effect（近似）：`DshModals.tsx:233-244` ≈ `PluginsModals.tsx:285-298`
- **影响**：颜色/文案/布局改一处漏三处（当前 `#ff4d4f` 等硬编码颜色即已出现两处）。
- **建议**：抽 `components/StepIcon.tsx`、`components/StepProgressList.tsx`（内含 upsert + 行渲染）、`components/ErrorDetailModal.tsx`，四个 modal 文件共用。

### M3. `ipc/profile.ts` 中 `cordis.patch.yml` 路径 + 读文件样板重复 9 处
- **文件:行号**：`src/main/ipc/profile.ts:75, 83, 109, 308, 320, 337, 351, 394, 410`
- **证据**：
  ```ts
  // 每处都是同款两行
  const path = join(profileDir(name), 'cordis.patch.yml')
  const current = existsSync(path) ? readFileSync(path, 'utf8') : '[]'
  ```
- **影响**：写路径若改动（如文件名调整）要改 9 处；且已有 `writeUserPatch`（72 行）却只有 `profile:addRow` 等少数在用。
- **建议**：补 `readUserPatch(name): string` 对称 helper，9 处收敛为 1。

### M4. 错误码双轨制：`E` 常量与裸字符串混用
- **文件:行号**：`src/main/ipc/profile.ts` 用 `fail(E.bundleNotFound)`（334）、`fail(E.nameInvalid)`（305）等，却又用 `fail('patch.writeVerify')`（116）、`fail('bundle.noRow')`（336）、`fail('patch.nothingToRemove')`（321）、`fail('name.invalid', [], '...')`（372）、`fail('shell.openPath')`（413）；`src/main/ipc/dsh.ts:206` `fail('dsh.protected')`、`:331` `fail('dsh.versionExists')` 亦然。
- **影响**：新代码不知道该用哪个；渲染层 `t('errors.<code>')` 对裸字符串无编译期校验，拼写错误只在运行时暴露。
- **建议**：全部收敛到 `E`（或单一 codes 枚举）；给 `errors.*` i18n key 加结构校验（如 en/zh 之外对 `E` 的 key 做存在性断言测试）。

### M5. `profile:setDisabled` 绕过了 `writeUserPatch` 的文档级校验，写路径不统一
- **文件:行号**：`src/main/ipc/profile.ts:105-121`
- **证据**：`setDisabled` 直接 `writeFileSync(patchPath, setRowDisabled(...))` + `verifyDisabledState` 校验；而 `addRow/removeRow/copyRow/setRowConfig` 走 `writeUserPatch` → `assertPatchDocValid`（拒绝"顶层非数组"等坏文档）。同一文件两条写入+校验路径。
- **影响**：未来对写安全做统一增强时，此 handler 会漏掉；两条路径行为不一致。
- **建议**：`setDisabled` 也改走 `writeUserPatch`（保留其专用 verify 作为附加断言）。

### M6. `ProfileDetail.tsx` 中 `load()` 与 useEffect 双实现，`load` 无竞态守卫
- **文件:行号**：`src/renderer/src/views/ProfileDetail.tsx:65-75`（`load`）与 `:77-94`（`useEffect` 内联同样逻辑）
- **证据**：`useEffect` 内带 `alive` 守卫；`load` 没有。所有变更 handler（`toggleProfile`/`submit`/`removeRow`……）都 `void load()`——快速切换 profile 时，旧请求迟到会覆盖新数据（effect 版本反而安全）。
- **影响**：重复逻辑 + 潜在陈旧数据竞态。
- **建议**：只留一个带守卫的 `load`（通过 `name` ref 或请求序号丢弃过期响应），effect 与 handler 共用。

### M7. preload 契约漂移：内联匿名类型替换 shared 命名类型
- **文件:行号**：`src/preload/index.ts:128`（`plugins.list` 返回内联 `{ name: string; version: string }[]`，正源 `InstalledPlugin` 在 `shared/api.ts:100`）；`:233`（`installOfficial` 参数缺 `force?: boolean`，正源 `shared/api.ts:205`）
- **证据**：`satisfies WindowApi` 因结构化兼容而放行，漂移在类型层不可见。
- **影响**：契约"单一事实来源"在此两处被绕过，字段增删静默脱钩。
- **建议**：preload 一律复用 shared 命名类型（文件其余 98% 已如此，仅这两处回归）。

### M8. IpcResult 错误处理模式全库 67 处重复，且 `unwrap()` 是死代码
- **文件:行号**：`src/renderer/src/lib/ipc.ts:24-28`（`unwrap`），全库 **0 调用**（grep 无命中）；`apiErrorText` 在 13 个文件出现 67 次，主导惯用法 `if (!r.ok) { void message.error(apiErrorText(r)); return }` 重复数十次。
- **影响**：`unwrap` 本是对该惯用法的抽象却无人使用——两条竞争惯用法并存；渲染层错误处理噪音大。
- **建议**：要么推广 `unwrap`/封装 `callApi`，要么删除 `unwrap`，收敛到单一写法。

### M9. 弹窗状态堆在页面组件（ProfileSection 8 组、DshSection 6 组）
- **文件:行号**：`src/renderer/src/views/ProfileSection.tsx:49-63`（create/clone/mirror/export/import + 各自 name 状态）；`DshSection.tsx:48-60`
- **影响**：页面组件仍承担大量弹窗开关 + 输入状态；`useRunRuntime`/`useTrash`/`usePluginDownloads` 已证明 hook 提取方向可行。
- **建议**：抽 `useProfileModals` / `useDshModals` hook，页面只剩列表编排。

### M10. 测试断言耦合实现细节（易碎）
- **文件:行号**：`src/main/core/plugins.test.ts:108`（断言 pnpm 参数**精确数组** `['add', 'foo@^1', '--fetch-retries=3', '--fetch-retry-maxtimeout=60000']` 且第三参 `undefined`）、`:139` 同款、`:320`（`expect(runPnpm).toHaveBeenCalledTimes(2)` 绑定"恰好两个 profile 需重装"）
- **影响**：调整重试标志等配置性改动即破坏无关测试；测试维护成本随配置决策波动。
- **建议**：仿照同文件 162-166 行风格——只断言 `args[0]==='add'` 与 source 串，不锁整串参数。

### M11. `ProfileDetail` 的 `useMemo` 依赖非稳定引用，memo 失效
- **文件:行号**：`src/renderer/src/views/ProfileDetail.tsx:59-63`（`layerLabel` 组件内函数）+ `:96-104`（`useMemo(..., [layers, layerLabel])`）
- **影响**：`layerLabel` 每渲染重建，memo 每次重算，`lastSeen` 的缓存意图落空（微性能 + 误导）。
- **建议**：`layerLabel` 移出组件（纯函数），或 memo 依赖改为仅 `[layers, t]`。

## 正面发现（无需修改，记录备案）
- **分层纯净**：core 不 import ipc/renderer/preload，renderer 不 import main（grep 零命中）；core 通过 `../../shared/types.ts` 单点取类型。
- **类型健康**：全库几乎零 `any`（仅测试中 2 处 `as unknown as`），无 `as any`。
- **契约护栏**：`shared/types.ts` 是唯一事实来源；`shared/api.ts` 定义 `WindowApi`，`preload/index.ts` 用 `satisfies WindowApi` 守住实现不漂移；`core/types.ts` 是干净转发层（非重复定义）。
- **core 测试质量高**：`plugins.test.ts`（546 行）用真实临时目录 + mock pnpm，覆盖迁移/作用域/级联卸载等边界；`pluginDownloads.test.ts` 用 `vi.mock` 隔离 pnpm，断言清晰。
- **i18n 结构安全**：`en.ts` 用 `const en: typeof zh` 强制双语文案同构。
- **hooks 提取方向正确**：`useRunRuntime`/`useTrash`/`usePluginDownloads` 已把运行/回收站/下载状态从页面剥离。

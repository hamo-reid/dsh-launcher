# 04 · 历史遗留审计报告（DSH Launcher）

> 审计方式：git 历史（52 个提交，dev 分支 HEAD = 2e455c9）与代码现状交叉验证，纯分析、未改动任何源码。
> 演进概览：项目从"单插件库 + 单 dsh 版本"的 v0.1.x 雏形，经过「dsh 官方安装 → 版本仓库/更新 → tray → Node 运行时 → 数据导出迁移 → 社区市场 → 多版本插件库 + 一次性迁移」六轮主线迭代，期间类型边界从 `main/core` 迁出到 `src/shared`、插件库从扁平布局改为 `archive/` 版本化布局，多个模块在合并中留下孤儿文件与失效兼容路径。

## 一、死代码 / 孤儿代码

### 1.1 `src/main/core/types.ts` —— 零引用的转发 shim（死文件）
- **文件**：`src/main/core/types.ts`（全文 27 行）
- **证据**：文件头注释自述"keeps the established `../core/types.ts` import path working"；但全仓 `grep "core/types"` 仅命中其自身注释与 `src/shared/types.ts` 的文档注释，**无任何文件 import 它**——所有 main/core 模块均直接 `import ... from '../../shared/types.ts'`（appState/combo/dsh/health/market/plugins/profile/settings/trash 等 20+ 处）。`vitest.config.ts:14` 还专门为它做了 coverage exclude。
- **影响**：误导（让人以为有第二份类型定义）；覆盖配置里留了专属排除项。
- **清理建议**：删除该文件，并同步移除 `vitest.config.ts:14` 的 exclude。**低风险，不动运行路径**（无引用）。

### 1.2 `dsh:detect` —— 被 `dsh:probe` 取代的重复 handler
- **文件**：`src/main/ipc/dsh.ts:168-172`、`src/preload/index.ts:222`、`src/shared/api.ts`（`dsh.detect`）
- **证据**：`dsh:detect` 与 `dsh:probe`（ipc/dsh.ts:303）在空 path 时调用**同一个** `probeDshs()`；渲染层只调用 `window.api.dsh.probe`（`DshModals.tsx:81`），`dsh:detect` 全仓零渲染层调用。属于早期"自动探测"入口被"可传路径的 probe"升级后残留。
- **影响**：双份 IPC 面 + preload + api 契约，纯冗余。
- **清理建议**：删 handler、preload `detect`、api.ts 条目。**低风险**（无调用方）。

### 1.3 `home:load` —— 无调用方的 IPC
- **文件**：`src/main/ipc/home.ts:13-21`、`src/preload/index.ts:95-96`
- **证据**：渲染层 `window.api.home.*` 仅使用 `home.setDisabled`（`ProfileDetail.tsx:113`）；`home:load` 零调用。core 侧 `homePatchPath`/`parsePatchRows` 仍被 `home:setDisabled` 使用，不受影响。
- **清理建议**：删 `home:load` handler 与 preload 暴露。**低风险**。

### 1.4 孤儿命名测试文件（3 个，模块名从未存在）
- **文件**：`src/main/core/dsh-install.test.ts`、`src/main/core/update.test.ts`、`src/main/core/onboarding.test.ts`
- **证据**：三者 import 目标分别是 `./dsh.ts`、`./dsh.ts`、`./settings.ts + ./appState.ts`；git 历史确认 `dsh-install.ts`、`update.ts`、`onboarding.ts` **从未被跟踪过**（`git log --all -- <file>` 为空）。文件头注释仍自称"Tests for the official-install pure helpers"（实际测 dsh.ts 的 `resolveInstallSpec`/`updateDsh` 等）。vitest 照常运行且通过（import 的是现存模块），故属于**命名与测试对象脱节**的遗留，非坏测试。
- **影响**：新人按文件名找模块会扑空；`ls src/main/core` 会出现三个"幽灵模块名"。
- **清理建议**：按被测模块改名（`dsh-install.test.ts → dsh.install.test.ts`、`update.test.ts → dsh.update.test.ts`、`onboarding.test.ts → settings.onboarding.test.ts`）。**低风险**。

### 1.5 死 i18n key（12 个 × 中英 2 语言）
- **文件**：`src/renderer/src/i18n/locales/en.ts`、`zh.ts`
- **证据**：脚本提取 540 个 key，逐一对 `t('...')` 字面量 + 全部 `t(\`...\${...}\`)` 动态模板（仅 4 处：health.kind/errors/download.status/plugin.source/dsh.official.step）比对，以下 key 既无字面也无动态生产者：
  `app.title`、`common.back`、`common.loading`、`dsh.action.removeConfirm`、`dsh.official.installed`、`dsh.update.latest`、`dsh.update.start`、`plugin.version.downloaded`、`plugin.market.addedToStore`、`plugin.installedStore`、`plugin.overview.builtin`、`plugin.overview.storeTag`
  （`errors.*`、`plugin.source.*`、`dsh.official.step.*` 为动态查找，**不算死 key**，已排除。）
- **清理建议**：删这 12 对 key。**低风险、纯文案**。

### 1.6 `market.ts` 过度导出的内部助手（生产仅内部/测试使用）
- **文件**：`src/main/core/market.ts`
- **证据**：`catalogUrl`(:90) 与 `cachedCatalog`(:96) 无任何外部 import；`loadMarket`(:135) 仅 `resolveMarket`(:113) 内部调用 + `market.test.ts` 使用；`forgetCatalog`(:85) 仅 `market.test.ts`(:203,:213) 使用。IPC 层只 import `installSpecFor/marketSourceState/pageCatalog/resolveMarket/setMarketSourceState`。
- **影响**：API 表面积偏大、`forgetCatalog` 为测试而存在的公共入口。
- **清理建议**：`catalogUrl/cachedCatalog` 改私有；`loadMarket/forgetCatalog` 保留但降级为内部 + 测试专用（或改 `_` 前缀约定）。**低风险**。

### 1.7 `vitest.config.ts` 悬挂 exclude
- **文件**：`vitest.config.ts:15`
- **证据**：exclude 列表引用 `src/main/core/combo.plugins.ts`，该文件不存在（git 从未跟踪），为 7bdc278 "remove the unused plugins workspace" 后的残留。
- **清理建议**：删除该行。**低风险**。

## 二、迁移 / 兼容遗留

### 2.1 插件库"一次性迁移"没有完成标记，每次写库都重扫旧布局
- **文件**：`src/main/core/plugins.ts`、`src/main/ipc/store.ts`、`src/renderer/src/App.tsx:70-101`
- **证据**：`migrateLegacyStore`（plugins.ts:253-322）在**每次** `installSource`/`addPlugin` 时无条件执行（:391），`listPlugins` 永远 UNION 扁平旧布局（`legacyListPlugins` :190-195），`installedStoreVersion` 保留 `readVersion(join(storeDir,'node_modules',name))` 扁平回退（:105）。`store:needsMigration`/`store:migrate`（ipc/store.ts）+ App.tsx 启动同意弹窗是用户侧"一次性"流程，但**判定基于"是否存在遗留文件"而非持久化完成标记**——迁移后这些扫描/弹窗探测逻辑仍永久驻留运行路径。
- **影响**：这是**有意的兼容设计**（真实老用户存储仍需读回），不算 bug；但"一次性"从未真正落盘，`needsStoreMigration` 每次启动探测、`legacyListPlugins` 每列一次列表全扫，属于为过渡期永久买单。
- **清理建议**：短期保留读兼容（勿删）；可考虑在迁移完成后写 `.pm-migrated` 标记，让探测逻辑若干版本后退役。**动运行路径，需谨慎（P1，见清单）。**

### 2.2 `DshEntry.versionDir` / `managed` 锚点 —— 有意的跨版本兼容，保留
- **文件**：`src/main/core/dsh.ts:289-300`、`src/shared/types.ts:129-137`
- **证据**：`versionDir` 记录"落到哪个版本仓库"，避免设置项变更后清理错位；`managed` 读侧合并路径推导（85a7036 引入）。类型注释明确写"Absent on legacy entries"，是**有意的演进兼容**。
- **结论**：非遗留债，**建议保留**，仅提示：该字段有真实迁移数据面（老条目无此字段），删除需走数据迁移。

### 2.3 回收站（soft-delete）无新旧并存
- **证据**：`src/main/core/trash.ts` + `src/main/ipc/trash.ts` + `src/renderer/src/views/useTrash.ts` / `TrashPanel.tsx` 单一实现自洽；`profile.ts` 只有 `softDeleteProfile`(:98) 一条删除路径（`deleteProfile` IPC → 软删 → `.trash`），未发现旧硬删残留或双实现。
- **结论**：该维度干净。

### 2.4 历史里的 squash+merge 重复提交（非代码债）
- **证据**：`844dd95` 为 merge 提交，把同功能的 squash 提交 `b1db280` 合入；两者 stat 一致。属提交历史观感问题，无代码残留。
- **结论**：仅记录，不清理。

## 四、废弃模式 / 结构性债务

### 4.1 跨进程契约三件套（types/api/preload）每功能必改 —— 边界未稳定
- **证据**（git log 文件改动频率）：`shared/types.ts` 14 次、`shared/api.ts` 18 次、`preload/index.ts` 17 次、`i18n/en.ts`+`zh.ts` 各 19 次——几乎每个功能提交都同时动契约三件套与双语文案，是**全仓最高频变更文件**。`src/main/core/types.ts` 转发 shim（见 1.1）正是这次"类型从 core 迁往 shared"的历史疤痕。
- **影响**：契约边界随功能反复重画，IPC 面增长无序（1.2/1.3 的冗余 handler 即其副产品）。
- **建议**：合并期将"加 IPC 方法"视作需要 review 的契约变更；至少把 1.1-1.3 清掉再谈稳定。

### 4.2 `plugins.ts`(898 行) 与 `dsh.ts`(554 行) —— 高频改动模块该拆
- **证据**：`plugins.ts` 7 次、`dsh.ts` 10 次改动（top 高频），且各堆叠了多块独立职责：plugins.ts 含「多版本布局 + 一次性迁移 + profile link 重写 + 卸载级联 + 来源追踪」，dsh.ts 含「官方安装 + 更新 + 版本仓库发现 + 可删判定 + home 处理」。迁移段（`migrateLegacyStore`+`rewriteProfileLinks`，:253-382 约 130 行）可独立成 `store-migration.ts`。
- **建议**：迁移逻辑抽模块；dsh.ts 按 install/update/repo 拆分。**重构风险中高（在运行路径上），见清单 P1。**

### 4.3 在途 WIP 已出现第二条安装路径（前瞻提示，非已提交遗留）
- **证据**：工作树未提交的下载面板特性（`pluginDownloads.ts` + `DownloadPanel.tsx` + hooks/）新增 `downloads:*` IPC，与既有 `plugins:add` 网络安装并行；`installSource` 正从私有改导出供其复用。当前 plugins.test.ts/plugins.ts/ipc/preload/api 均有未提交改动。
- **结论**：合入后 `plugins:add` 与 `downloads:start` 将并存两条"装插件"入口，建议在特性合入时决定去留，避免再留一对冗余 handler（同 1.2 模式）。

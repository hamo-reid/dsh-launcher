# 01 · 代码结构梳理（轮1 · 了解）

> 目的：为后续三维度审计提供结构地图。本文档仅做客观梳理，不评判优劣。

## 1. 构建与入口

- `electron.vite.config.ts`：main 使用 `externalizeDepsPlugin()` 外部化依赖；
  preload 无插件（默认打包）；renderer 使用 `@vitejs/plugin-react`。
- 入口链：`src/main/index.ts`（226行，应用生命周期 + 单实例 + 窗口创建）→
  `src/preload/index.ts`（303行，contextBridge）→ `src/renderer/src/main.tsx`。
- 构建产物：`out/`，打包脚本 `pack:portable` / `pack:dir` 走 electron-builder
  （asar + `asarUnpack: **/sql.js/**`，因 sql.js 的 wasm 需解包）。

## 2. 主进程核心（`src/main/core/`）领域划分

按业务域组织，每域通常成对出现 `*.ts` 业务实现 + `*.test.ts` 单测：

- **Profile 域**：`profile.ts`、`home.ts`、`home-data.ts`、`combo.ts`、`patch.ts`、
  `manifest.ts`、`trash.ts`（软删除回收站）、`appState.ts`（应用级状态）。
- **dsh 运行时域**：`dsh.ts`、`dsh-install.test.ts`、`node-env.ts`（Node 环境探测）。
- **插件/市场域**（近期主战场）：`plugins.ts`、`pluginDownloads.ts`、`market.ts`、
  `pnpm.ts`（pnpm 作为插件安装器）、`npm.ts`。
- **外部运行时工具**：`app-util.ts`（路径/工具解析）、`errors.ts`（错误类型）、
  `logger.ts`、`settings.ts`、`version.ts`、`update.ts`、`health.ts`。
- 类型：`types.ts`（26行，主进程内部类型）。

## 3. IPC 桥接层（`src/main/ipc/`）

每文件对应一条业务链路，注册 `ipcMain.handle` / `ipcMain.on`：
`profile.ts`(437行)、`dsh.ts`(381行)、`plugins.ts`(254行)、`run.ts`(250行)、
`settings.ts`(162行)、`market.ts`(64行)、`home-data.ts`(84行)、`trash.ts`(41行)、
`home.ts`(34行)、`window.ts`(60行)、`logs.ts`(19行)、`store.ts`(35行)。

统一返回 `IpcResult<T>`（见 `src/shared/types.ts`，承载成功/失败与错误码）。

## 4. 渲染层（`src/renderer/src/`）

- **视图**（`views/`）：页面级组件，按 dsh/profile/plugin/market/settings 划分。
  - `DshModals.tsx` **715行**、`ProfileModals.tsx` 479、`ProfileDetail.tsx` 451、
    `PluginsSection.tsx` 453、`DshSection.tsx` 325 —— 页面级文件偏大。
- **组件**（`components/`）：复用型 UI（Panel、NavList、RunConsole、StatusTag 等）。
- **自定义 hooks**（`views/` 内嵌 + `hooks/`）：`useRunRuntime.tsx`、`useTrash.ts`、
  `usePluginDownloads.ts`。
- **i18n**：`i18n/locales/{en,zh}.ts`，双语。**状态/数据流**：通过
  `src/renderer/src/lib/ipc.ts` 调用 `window.api`，未引入全局状态库（如 Redux/Zustand）。

## 5. 关键数据流

```
渲染层视图 → lib/ipc.ts → window.api.* (preload contextBridge) → ipcRenderer.invoke
  → 主进程 ipc/*.ts handler → core/*.ts 业务逻辑 → 文件系统 / sql.js(SQLite) / pnpm
  → IpcResult<T> 原路返回 → 视图刷新
```

- 插件安装链路：`plugins.ts` + `pluginDownloads.ts`（下载器）+ `pnpm.ts`（安装到 profile），
  前端 `MarketSection.tsx` / `DownloadPanel.tsx` / `usePluginDownloads.ts`。
- 运行链路：`run.ts` → `core/dsh.ts` 启动 profile 的 dsh，控制台 `RunConsole.tsx`。

## 6. 测试现状（客观统计）

- 主进程 core 域基本每模块配套单测：`*.test.ts` 分布密集（app-util/appState/combo/
  dsh/errors/home/home-data/logger/manifest/market/node-env/npm/onboarding/patch/
  profile/settings/trash/update/version + 新增 plugins/pnpm/pluginDownloads）。
- 渲染层测试极少：`i18n.test.ts` 仅 1 处；视图/组件无单测。
- `vitest.config.ts`、`coverage/` 目录已存在（说明曾跑过覆盖率）。

## 7. 交给后续审计的线索（供轮2剪裁）

- 可维护性：页面级大文件（715/479/451…）、`ipc/` handler 厚度（437/381/254）、
  渲染层测试缺失、命名/重复是否成问题 → 见 [02](./02-可维护性审计.md)。
- 安全：IPC 通道达 100+，入口参数校验是否充分；child_process/pnpm/shell 调用点；
  sql.js/解压 zip/adm-zip 是否会注入 → 见 [03](./03-代码安全审计.md)。
- 遗留：近期多轮插件/market 迭代 + tsbuildinfo/coverage 产物 + 版本演进痕迹 →
  见 [04](./04-历史遗留审计.md)。

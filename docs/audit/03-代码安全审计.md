# DSH Launcher 代码安全审计报告

**审计范围**：src/main（Electron 主进程 + IPC + core）、src/preload、src/renderer（渲染层 XSS 面）、package.json / electron-builder 配置、关键依赖版本。
**审计方式**：静态代码审计（仅分析，未改动任何源码）。
**日期**：2026-08-25

---

## 风险总评（一句话）

**未发现可直接利用（无需先攻陷渲染层）的远程/本地漏洞，但存在 1 个真实的 shell 注入写法、多处"渲染层失陷后即达"的路径穿越/任意删除原语，以及若干 Electron 纵深防御缺口——整体安全基线良好（contextIsolation、无 dangerouslySetInnerHTML、rehype-sanitize、spawn 数组参数），关键风险全部集中在"渲染进程被攻破后能做什么"，因此渲染层锁定（CSP + README 净化）是本应用最重要的防线，目前这条防线总体有效。**

> 所有 IPC 通道均未做 `event.senderFrame` 来源校验，且存在 `plugins:*` / `trash:*` / `profile:launch` 等接受任意字符串、直接拼进路径或 shell 命令的处理器。由于渲染层是沙箱 + contextIsolation + 无 nodeIntegration，上述原语**目前**只能被"已被攻破的渲染进程"调用；但任何一个 XSS 或供应链事件都会把下列 🟡 项升级为**任意文件读写 / 任意命令执行**，故按纵深防御要求一律给出修复建议。

**未发现达到"真实可利用（不依赖渲染层失陷）"级别的高危项。** 以下为最接近高危、务必优先处理的项目（因当前无渲染层调用方/被 sanitize 拦截，降级为中危，但修复成本低、收益高）：

## 🟡 中危

### 1. `profile:launch` —— shell 命令字符串拼接注入（【真实可利用 · 死代码通道】）

- **文件**：`src/main/ipc/profile.ts:419-437`
- **证据**：
  ```ts
  // :424
  const command = `${baseLaunch(entry.execPath)} --profile ${name}`
  // :427  Windows
  spawn('cmd.exe', ['/c', 'start', `"dsh ${name}"`, 'cmd', '/k', command], { detached: true, stdio: 'ignore', env }).unref()
  // :431  POSIX
  spawn(command, { detached: true, stdio: 'ignore', shell: true, env }).unref()
  ```
- **问题**：`name`（渲染层参数）与 `execPath`（`dsh:add`/`dsh:addManual` 注册，渲染层可控）被**字符串拼接**进 `cmd.exe /c ... cmd /k <command>` 命令串，`name` 在 `cmd /k` 段**未加引号**。Windows 下 `name = "foo & calc"` 即任意命令执行；POSIX 分支 `shell: true` 同理。`name` 此处**未做任何校验**（`createProfile`/`importProfile` 有 kebab-case 校验，但该处理器没有）。
- **利用条件**：① 当前渲染层无任何调用方（`useRunRuntime` 走 `run:start`，`profile:launch` 是未接线的通道），但已通过 preload `window.api.profile.launchProfile` 暴露；② 需渲染进程已失陷（XSS 等）才能调用。属于**潜伏的注入点**。
- **对比**：正确实现 `run:start`（`src/main/ipc/run.ts:170-178`）用 `spawn(exe, argv, { shell: false })` 数组参数，安全。本处是代码库中**唯一**的 shell 串拼接。
- **修复建议**：直接删除该通道，或改写为 `spawn(exe, [script, '--profile', name], { shell: false })`（数组参数 + 显式 shell:false），并在入口对 `name` 做 `/^[a-z0-9][a-z0-9-]*$/` 校验。**P0**。

### 2. `will-navigate` 仅拦截 http(s)，`file:` / 其它 scheme 导航未阻止（【加固建议】）

- **文件**：`src/main/index.ts:106-111`
- **证据**：
  ```ts
  win.webContents.on('will-navigate', (event, url) => {
    if (/^https?:/i.test(url)) { event.preventDefault(); void shell.openExternal(url) }
  })
  ```
- **问题**：逻辑是"只拦 http(s)"，即 **`file://`、`about:`、任意 scheme 的导航全部放行**。打包后应用本身以 `file://.../index.html` 加载；一旦渲染层出现 XSS 或未来代码执行 `location.href = "file:///C:/.../x.html"`，会加载任意本地 HTML **且该页面继承 preload 的 `window.api`**（contextBridge 跨导航保持暴露），相当于把整个 IPC 面交给一个攻击者可控页面。正确写法应为 `if (url 不是应用自身页面) { event.preventDefault() }`。
- **利用条件**：需渲染层已失陷（XSS）或有可控的跳转入口；README 的 `<a>` 已被 rehype-sanitize 剥掉 `file:` href，RunConsole 链接也只会走 `openExternal`（仅 http(s)），故当前无现实触发路径，属纵深防御缺口。
- **修复建议**：改为默认拒绝 + 白名单放行（如 `url.startsWith('file://') && url 指向应用自身 index.html`，或直接 `if (!url.startsWith(app 自身加载地址)) event.preventDefault()`）。**P1**。

### 3. 插件/版本/档案名标识符未校验 —— 路径拼接原语（【加固建议】）

- **文件**：`src/main/core/plugins.ts`
  - `:50-52` `pluginVersionDir = join(versionsRoot(storeDir), name, version)`
  - `:56-58` `versionStagingDir = join(versionsRoot(storeDir), name, '.staging')`
  - `:386-434` `installSource`：`rmSync(staging)` / `mkdirSync(staging)` / `renameSync(staging, dest)` 全部基于渲染层可控的 `name`
  - `:582-616` `removePlugin`：`pRoot = join(versionsRoot(dir), name)` → `deleteTreePhysical(pRoot)`（**任意目录删除**）
  - `:851-899` `installIntoProfile`：`:865` `const dir = join(baseProfilesDir ?? profilesDir(), profile)` → `:869` 改写目标 `package.json` → `:877` 在该目录 `runPnpm(dir, ['install'])`
- **入口**：`plugins:add` / `downloads:start`（name）、`plugins:remove` / `plugins:uninstall`（name）、`plugins:installToProfile`（profile, pkg, version, dshId），见 `src/main/ipc/plugins.ts:76-151`。`trash:restore` / `trash:delete` 同理（`src/main/core/trash.ts:39-41,105-123`，`join(trashDir(), name)` → `renameSync`/`rmSync(recursive)`）。
- **问题**：`name`/`profile`/`version` 等标识符**未做 `..` / 绝对路径 / 非法字符过滤**。渲染层失陷后可：用 `name="../xxx"` 让 staging/archive 写到 store 外；用 `profile="../../任意目录"` 改写任意含 package.json 的目录并在其中跑 pnpm install；用 `trash:delete` 的 `name="../../任意目录"` **递归删除任意目录**。当前 UI 正常路径下这些值来自文件系统枚举（kebab 名）或目录选择框，故正常使用无风险。
- **修复建议**：在 IPC 入口对 `name`/`profile`/`version`/`pkg` 统一做白名单校验（profile 名 kebab-case；npm 名匹配 `NPM_NAME_RE`（market.ts:23 已有现成正则）；版本仅允许 `[0-9A-Za-z.+-]+`），并拒绝任何包含 `..`、`/`、`\` 的路径型标识符。**P1**。

### 4. CSP 不完整：无显式 `script-src`/`connect-src`/`object-src`/`base-uri`，`img-src` 含 `file:` 与 `http/https`（【加固建议】）

- **文件**：`src/renderer/index.html:6`
- **证据**：
  ```html
  <meta http-equiv="Content-Security-Policy"
    content="default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https: http: file: blob:" />
  ```
- **问题**：① 无 `script-src`（回退 `default-src 'self'`，可接受但建议显式）；② 无 `connect-src` / `object-src` / `base-uri` / `form-action`；③ `img-src` 放行 `https:`/`http:` 意味着 README 可外链任意图（跟踪面），放行 `file:` 意味着配合 PluginsModals 的 `file://` 图片加载可把任意本地文件当图加载（见 🟢-1）。
- **利用条件**：无独立漏洞；属纵深防御弱化。
- **修复建议**：补 `script-src 'self'`、`connect-src 'self'`、`object-src 'none'`、`base-uri 'self'`；若 README 外链图非必需，可将 `img-src` 收紧为 `'self' data: blob:`。**P1**。

### 5. `sandbox` 未显式声明（【最佳实践（非漏洞）】）

- **文件**：`src/main/index.ts:44-48`
- **证据**：`webPreferences` 仅有 `preload` / `contextIsolation: true` / `nodeIntegration: false`，未写 `sandbox`。
- **问题**：Electron ≥20 渲染进程默认 sandbox=true，且 preload 只用了 `contextBridge`+`ipcRenderer`（沙箱兼容），故当前**实际已沙箱化**。但未显式声明，未来若给 preload 引入 Node API（fs 等）会静默失去沙箱。
- **修复建议**：显式加 `sandbox: true`。**P2**。

## 🟢 低危 / 加固建议

### 1. README `<img>` 组件把相对路径拼成 `file:///` 任意本地路径（【加固建议】）

- **文件**：`src/renderer/src/views/PluginsModals.tsx:23-29`
- **证据**：
  ```tsx
  img: props => {
    const raw = props.src ?? ''
    const src = dir !== '' && !/^[a-z]+:/i.test(raw)
      ? `file:///${dir.replace(/\\/g, '/')}${raw.startsWith('/') ? '' : '/'}${raw}` : raw
    ...
  }
  ```
- **问题**：恶意插件 README 可写 `<img src="../../../../Users/x/secret.png">`，经此组件变成 `file:///<插件目录>/../../../../Users/x/secret.png` 被当作图片加载 → 把插件目录外的本地图片文件**读入页面**。受制于：① 仅 `img`（SVG 在 img 上下文不执行脚本）；② rehype-sanitize 默认 schema 已把 `file:`/`data:`/`javascript:` 从 `src` 剥除（已验证安装版 schema：`src` 仅允许 http/https），`file://` 只可能由本组件对"无协议相对路径"自行拼出；③ 渲染层 `connect-src 'self'` 无外联通道，像素数据无法外传。故实际影响≈本地文件存在性探测 + 图片内容本地展示。
- **修复建议**：对 `raw` 先做路径净化（拒绝含 `..` 或 `\` 的相对路径），或将解析后的文件路径交由主进程 `plugins:readme` 侧（`inlineRelativeImages` 已内联，可让渲染层**不再自行拼接 file://**）。**P2**。

### 2. `inlineRelativeImages` 把本地文件内联成 `data:` URL，且与 rehype-sanitize 的 src 协议白名单冲突（【最佳实践（非漏洞）】）

- **文件**：`src/main/core/app-util.ts:42-60`
- **问题**：主进程把 README 中已存在且为图片扩展名的相对引用改写为 `data:image/*;base64,...`。而 rehype-sanitize 默认 schema 的 `src` 协议白名单为 `http/https`（见 🟡-4 验证），`data:` 会被剥离——即**内联图片大概率渲染不出来**（功能缺陷，非安全问题）。同时 `mime` 仅按扩展名判定，`.svg` 也被内联为 `data:image/svg+xml`（img 上下文不执行脚本，无实际风险）。
- **修复建议**：二选一——给 sanitize 传自定义 schema 显式允许 `img[src]` 的 `data:` 协议（收紧其它），或改由渲染层 `img` 组件按 `dir` 拼相对 `file://` 并做路径净化。**P2**。

### 3. IPC 全通道无 `senderFrame` 来源校验（【最佳实践（非漏洞）】）

- **文件**：`src/main/ipc/*`（全部 `ipcMain.handle`，如 `src/main/ipc/plugins.ts:56` 起）
- **问题**：所有处理器均未校验 `event.senderFrame.url`/`event.senderFrame === webContents.mainFrame`。若渲染层出现可注入 iframe 或其它 frame 场景，无法区分来源。当前 `nodeIntegrationInSubFrames` 未开、preload 只在主 frame 生效，实际风险低。
- **修复建议**：对写操作通道统一加 `if (event.senderFrame?.url 不在应用自身来源) return fail(...)` 的公共守卫。**P2**。

### 4. `cordis.patch.yml` 行级编辑的 `id` 未校验，patch 文档允许 `!!js`（【加固建议】）

- **文件**：`src/main/core/patch.ts:100-113,254-263`、`src/main/ipc/profile.ts:302-315,57-70`
- **问题**：`profile:addRow` / `profile:setDisabled` / `home:setDisabled` 的 `id` 仅要求非空，随后被拼进 `- id: ${id}` 写入 `cordis.patch.yml`。该文件被 dsh 以**支持 `!!js` 自定义标签**的 YAML 加载（模板注释明示 `!!js` 允许）。渲染层失陷后可用含换行/特殊字符的 `id` 向 patch 注入 YAML 片段，最终由 **dsh 进程**（用户自己的运行时）执行。本应用进程本身不解析该 YAML（仅行级文本编辑 + `assertPatchDocValid` 对含 `!!js` 的文档跳过深校验），故属"诱导用户运行恶意 profile"的间接面。
- **修复建议**：对 `id` 做白名单校验（如 `/^[A-Za-z0-9._-]+$/`，行级编辑基于该正则已有 `ID_RE`）。**P2**。

### 5. `profile:import` 将导入 JSON 的 `userPatch` 原样写入（【最佳实践（非漏洞）】）

- **文件**：`src/main/core/profile.ts:394,406`
- **问题**：导入的 `cordis.patch.yml` 内容原样落盘，含 `!!js` 时 `assertPatchDocValid`（ipc/profile.ts:57-70）跳过校验。属应用设计功能（用户导入自己的配置），非应用进程注入。
- **修复建议**：导入时对 patch 做大小上限（防磁盘占用）并在 UI 明示来源不可信。**P2**。

### 6. `data:import` 可覆盖 dsh home 下的 `.env` / `.credentials.yaml` / `settings.yaml`（【加固建议】）

- **文件**：`src/main/ipc/home-data.ts:63-71` → `src/main/core/home-data.ts:182-198`（`importDshData` → `restoreHome`），`MIGRATABLE_TOP_LEVEL` 含 `.credentials.yaml`/`.env`/`settings.yaml`（`:30-41`）
- **问题**：`file` 路径由渲染层回传（虽来自 `data:inspectImport` 对话框）。渲染层失陷后可传任意 zip 路径，将其内容还原到 dsh home，覆盖用户凭据/配置；随后 dsh 下次启动可能读取被替换的 `.credentials.yaml`。属该功能固有行为 + 渲染层失陷前置。
- **修复建议**：`data:import` 改为在**主进程内**用对话框选文件并直接传递路径（不经过渲染层回传），或对 file 路径做 `resolve()` 后存在性校验。**P2**。

### 7. `run:start` shell 模式 ps1 无 BOM，Windows PowerShell 5.1 按 ANSI/GBK 误读非 ASCII（【最佳实践（非漏洞）】）

- **文件**：`src/main/ipc/run.ts:108-119`
- **证据**：`writeFileSync(scriptPath, script)`（默认 utf8 无 BOM），再 `powershell.exe -File scriptPath`。
- **问题**：Windows PowerShell 5.1 读无 BOM 脚本按系统 ANSI 码页（中文系统 GBK）。`exe`（`process.execPath`）若在含中文的用户目录下（如 `C:\Users\张三\...`），脚本可能被误读导致 shell 模式启动失败/命令错乱。`psQuote` 单引号转义本身正确，不构成注入；属正确性/健壮性问题。
- **修复建议**：写 ps1 时加 UTF-8 BOM（`Buffer.concat([Buffer.from([0xEF,0xBB,0xBF]), Buffer.from(script)])`）。**P2**。

### 8. 供应链风险提示（【仅提示，不开枪】）

- **文件**：`src/main/core/pnpm.ts`（`pnpm add` 任意 npm/github/file 源）、`src/main/core/plugins.ts:202-205,386-434`、`src/main/core/market.ts:259-267`
- **问题**：应用按设计从 npm registry / GitHub / 本地 zip **下载并安装任意第三方包**，之后由 dsh 加载执行。pkg 完整性仅依赖 registry HTTPS + 无固定 lockfile 校验（store 是动态 pnpm 工程）。若下载源被投毒（registry 账号失陷、GitHub 仓库被接管、用户手动指定镜像），等于把任意代码送进用户 profile。`installSpecFor` 的 npm 名/GitHub URL 正则（market.ts:23,270-282）已正确挡住注入型 spec，此处仅提示：安装前可校验 `package.json` 的 `dist.integrity` / `dist.tarball` 签名，并在 UI 对 `github:` 源标注非官方风险。
- **修复建议**：P2，供应链加固（记录每个安装源的 integrity 摘要，升级时比对）。

### 9. asarUnpack `sql.js` —— 逆向面提示（【最佳实践（非漏洞）】）

- **文件**：`package.json`（`build.asarUnpack: ["**/sql.js/**"]`）
- **问题**：sql.js 的 wasm 必须解包才能被 Node 加载（功能性要求）。但主进程/渲染层 JS 本身就在 asar 内明文可读，Electron 应用逆向门槛本就低——`asarUnpack` 不额外降低安全性，仅提示：不要在 asar 或 wasm 中存放任何机密（token、密钥）。**P2**。

### 10. README 外链图片 / 无 `rel="noreferrer"` 以外问题（【最佳实践（非漏洞）】）

- **文件**：`src/renderer/src/views/PluginsModals.tsx:20`（`a` 组件 `target="_blank" rel="noreferrer"`）
- **问题**：`target="_blank"` 链接被主进程 `setWindowOpenHandler`（index.ts:102-105）拦截并走 `shell.openExternal`（系统浏览器，非应用内），安全。README 外链图（`img-src https:`）可形成跟踪面，无更多风险。
- **修复建议**：无需处理；若在意隐私可在 CSP 收紧 `img-src`。**P2**。

## 【安全加固优先级清单】

### P0 —— 必须立即处理
1. **`profile:launch` shell 串拼接注入**（`src/main/ipc/profile.ts:424-432`）：删除该通道，或改为 `spawn(exe, [script, '--profile', name], { shell: false })` 并对 `name` 加 kebab 校验。这是代码库中唯一的 shell 注入写法，修复成本最低、一旦被任何未来代码调用即为 RCE。

### P1 —— 应尽快处理
2. **`will-navigate` 补全 scheme 拦截**（`src/main/index.ts:106-111`）：改为"非应用自身加载地址一律 `preventDefault`"，封死 `file:`/其它 scheme 导航继承 preload 面的路径。
3. **IPC 标识符校验**（`plugins:*` / `trash:*` / `installToProfile`）：对 `name`/`profile`/`version`/`pkg` 统一白名单校验，拒绝 `..`、`/`、`\`、绝对路径（复用 `market.ts:23` 的 `NPM_NAME_RE`），封死"渲染层失陷后任意目录写/删/跑 pnpm"的原语。
4. **CSP 补全**（`src/renderer/index.html:6`）：显式 `script-src 'self'`、`connect-src 'self'`、`object-src 'none'`、`base-uri 'self'`；评估收紧 `img-src`（去掉 `file:` / 外链 http/https）。

### P2 —— 加固项
5. 显式 `sandbox: true`（`index.ts:44-48`）。
6. IPC 加 `senderFrame` 来源守卫（公共包装）。
7. README `img` 组件路径净化，禁止 `..`（`PluginsModals.tsx:23-29`）；`inlineRelativeImages` 的 `data:` 与 sanitize 协议白名单冲突处理（二选一，见 🟢-2）。
8. patch 行编辑的 `id` 白名单校验（`patch.ts` / `ipc/profile.ts`）。
9. `data:import` 路径改为主进程内对话框直取（`ipc/home-data.ts`）。
10. `run:start` shell 模式 ps1 写 UTF-8 BOM（`run.ts:117`）。
11. 供应链加固：记录下载源的 integrity 摘要并在升级时比对；对 `github:` 源标注非官方风险（`market.ts` / `plugins.ts`）。
12. 逆向提示：禁止在 asar / sql.js wasm / 代码内放置任何机密（`package.json` asarUnpack）。

# DSH Launcher v0.4.0-beta2

> 本版主线是**统一数据根目录**：插件库、技能库与 DSH 版本库不再各自配置，改由一个数据根派生，并支持带校验的整体迁移。同时修掉了一个让 pnpm 安装下的官方 bundle **全部显示为缺失**的解析缺陷（它还会静默改写 profile 的 bundle 列表），并让 Profile / 运行两页各自记住所选的 DSH。**本版含破坏性变更**，建议升级前备份 `~/dsh-launcher`。

### 中文版

#### ⚠️ 破坏性变更

- **设置 schema 从 1 升到 2。** 影响两条路径：
  - **降级会丢数据根设置**：回到 ≤ 0.4.0-beta1 后，旧版本的白名单不认识 `dataRoot` 字段，**任何一次设置写入都会把它清除**。数据仍在磁盘上，只是不再被引用——如需降级，**先记下当前数据根路径**（设置页「目录」面板里可复制）。
  - **设置导出文件不再向下兼容**：由本版导出的 `settings.json` 会被旧版本**拒绝导入**（这是有意的保护，不是错误），而不是静默丢弃其中的数据根。
  - 升级方向不受影响：本版可以正常读取旧版本的设置与导出文件。
- **pnpm 安装下的 Profile 会开始显示出此前看不到的 bundle 层。** 这些层一直存在、一直参与宿主的启动组合，只是启动器此前解析不到它们。实测一个声明了 4 个官方 bundle 的 profile，插件列表从 **0 行变成 197 行**。这**不是新增插件**。
  - 随之而来的是**冲突检测开始把这些层纳入计算**：同一个 loader entry id 被多层 `insert` 时，本版会点名冲突的层并拒绝启动。这是宿主本来就会硬失败的组合——如果你装了自带 roster 的第三方 app bundle，可能第一次看到这条提示。

#### ✨ 新功能 · 统一数据根目录

- **一个根，派生三个目录**：`<数据根>/plugins`、`<数据根>/skill-library`、`<数据根>/dsh/versions`。此前插件库与版本库各有一个设置项，技能库则是写死在代码里的——现在三者在设置页「目录」面板里统一由一个根决定，面板会实时列出它们当前解析到的实际路径。
- **默认零迁移**：数据根未设置时等于 Electron 的 `userData` 目录，因此**升级后的磁盘布局与之前逐字节相同**，什么都不用搬。
- **迁移是显式的、可预览的**：填好新根后点「迁移数据到新位置」，先看到一张预览表（每项的当前位置、新位置、条目数、目标是否已占用），再确认执行。迁移过程是**复制 → 校验（逐文件比对大小）→ 切换**，**旧目录一律保留**，确认无误后由你自己删除。
  - **部分失败不会切换**：只要有一项没复制成功，设置就保持指向原位置，并逐项报出失败原因。重试是安全的——已经复制到位的项会被识别并跳过。
  - **目标已占用时先改名归档**：`<目录>.before-migration-<时间戳>`，而不是把新旧内容合并成一半一半。
  - **缓存不迁移**：pnpm 的 `.pnpm-store` 会被跳过（可重建，且可能有好几 GB），界面里也写明了这一点。
  - **有 profile 在运行时拒绝迁移**，避免复制正在被使用的可执行文件与 home。
- **profile 不在数据根的范围内**：它们恒为 `<dsh home>/profiles`，这是宿主自己的契约（直接运行 `dsh` 时读的是同一个位置），启动器不会把它挪走。设置页的说明里写清了这一点，也写清了设置数据库与日志同样留在 `userData` 下。
- **旧位置仍有数据时会提示**：如果你之前单独指定过插件库或版本库的位置，面板会指出「旧位置仍有数据」，但不会替你删除。

#### ✨ 新功能 · 界面

- **Profile 页与运行页各自记住所选的 DSH**：此前切换标签页会卸载整个分区，选择随之重置回第一个已注册的 dsh——关掉应用重开也一样。现在两页各自记住自己的选择（存于本地，与主题、插件筛选器同一处），且**互相独立**：用于浏览 profile 的 dsh 与用于启动的 dsh 未必是同一个。
  - 记住的 dsh 如果已被移除，会自动回退到第一个已注册的 dsh，不需要手工清理。
- **运行页的 DSH 选择器移到了左侧栏顶部**，与 Profile 页一致——切换启动目标不再需要滚回内容区顶部。

#### 🐛 修复

- **pnpm 安装下的官方 bundle 全部被报告为「缺失」**。bundle 解析此前是「node_modules 根 + 包名」的路径拼接，而 pnpm 只把**直接依赖**链接到 `node_modules/@deepseek-ai/` 下——那里只有 `dsh` 一个，其余官方 bundle 都是它的**传递依赖**，躺在 `.pnpm/<包>@<版本>_<哈希>/node_modules` 里。于是：
  - 校验把健康的 profile 判为「有缺失、无法启动」；
  - 插件列表与层栈**静默跳过**这些层（组合出的插件行数为 0）；
  - 最严重的一条：**「重新对齐」会把它们从 profile 的 `dsh.profile.bundles` 里删掉**——因为是按「解析不到 = 没装」判定的。
  - 现在解析走 dsh 安装自身的位置：沿 Node 的查找链、从**真实路径**（symbolic link/junction 的原始路径不在任何查找链上）出发，四个官方 bundle 全部命中。
- **迁移 DSH 版本库时的重试会漏掉 home 目录**。版本库和它旁边的 `homes/` 是不可分的（home 恒为 `<版本库父目录>/homes/<名称>`），但完成判定只看版本库本身。一次「版本库复制成功、某个 home 失败」的尝试之后，重试会认为已经搬完并跳过——于是每个 dsh 的 home 指向一个永远不存在的目录。现在完成判定同时覆盖版本库与每个实例的 home。
- **一个失效的链接会让整个迁移失败**。复制采用 dereference，遇到目标已消失的 junction（一次安装升级就会留下这种）会抛 `ENOENT`。现在这类条目被跳过：它背后没有内容可丢，也不该由它挡住整次迁移。

#### ⚡ 优化

- **组合解析的搜索根每次组合只算一次**。构建搜索根要向上定位 dsh 安装锚点并编译一条 Node 查找链，而 profile 组合的每个 bundle 都在重算它；经过 profile 列表页会放大成「profile 数 × bundle 数」次同步文件系统调用。改为每次组合算一次后传递下去，单次解析的调用方不受影响。

#### 🏗️ 工程 / 架构

- **磁盘解析独立为 `core/store/module-resolve.ts`**，由 `combo.ts` 与 `module-index.ts` 共用。此前两者各有一套「这个包在哪」的实现，其中只有一套理解 pnpm 布局——这正是上面那个 bug 的根源。抽出后二者共用同一条链，且不产生循环依赖（`module-index.ts` 反向引用了 `combo.ts` 的插件列表）。
- **两个 bundle 判据被明确区分并写在注释里**：一个 bundle「有没有 patch 文件」与「有没有声明 patch」是两件事，后者是「重新对齐」删除层的唯一依据，二者不可混用。
- 移除 `dsh:setVersionDir` / `plugins:setDir` 两个通道与 `setVersionDirValue`：数据根成为这三处目录的唯一写入口，安装对话框里填的「本次安装位置」不再静默写回设置。
- **测试从 794 项 / 64 文件增至 829 项 / 67 文件**，其中新增了针对 pnpm 布局、断链、以及「一半搬完」状态的回归用例——后者此前没有覆盖，正是它让重试路径上的缺陷躲过了检查。
- 无新增运行时依赖。

### English

> This release is about the **unified data root**: the plugin store, the skill library and the DSH version repo stop being configured separately and derive from one root, with a verified migration path. It also fixes a resolution defect that made every official bundle show as **missing** on a pnpm install — a defect that also silently rewrote a profile's bundle list — and lets the Profile and Run pages each remember the DSH they are pointed at. **This release carries breaking changes**; back up `~/dsh-launcher` before upgrading.

#### ⚠️ Breaking changes

- **The settings schema goes from 1 to 2.** Two paths are affected:
  - **Downgrading loses the data-root setting**: back on ≤ 0.4.0-beta1, the older whitelist does not know the `dataRoot` field and **any settings write clears it**. The data is still on disk, just no longer referenced — note the current root path **before** downgrading (the Directories panel can copy it).
  - **Exported settings no longer load downwards**: a `settings.json` exported by this version is **refused** by an older one (a deliberate guard, not an error) rather than silently dropping the data root from it.
  - Upgrading is unaffected: this version reads older settings and older exports normally.
- **Profiles on a pnpm install will start showing bundle layers that were never visible before.** They were always there and always part of what the host composed; the launcher simply could not resolve them. Measured on a profile declaring four official bundles: the plugin list goes from **0 rows to 197**. This is **not new plugins**.
  - Consequently, **conflict detection now includes those layers**: when one loader entry id is inserted by more than one layer, this version names the colliding layers and refuses to launch. That combination would already hard-fail the host — if you use a third-party app bundle that ships its own roster, you may see this reported for the first time.

#### ✨ Features · Unified data root

- **One root, three derived directories**: `<root>/plugins`, `<root>/skill-library`, `<root>/dsh/versions`. The plugin store and the version repo each had their own setting and the skill library was hardcoded; all three now follow a single root, and the Directories panel lists the paths they actually resolve to.
- **Zero migration by default**: an unset root means the Electron `userData` dir, so the **on-disk layout is byte-identical to before** and nothing has to move.
- **Relocating is explicit and previewable**: fill in a new root, hit "migrate data", and you get a table of what would move where — current location, new location, entry count, whether the destination is occupied — before anything happens. The move is **copy → verify (per-file size comparison) → switch**, and **the old directories are always kept** for you to delete once satisfied.
  - **A partial failure never switches**: if any item fails, the settings keep pointing at the old location and each failure is reported. Retrying is safe — anything already copied is recognised and skipped.
  - **An occupied destination is archived first**, as `<dir>.before-migration-<timestamp>`, rather than merged into a half-old/half-new mix.
  - **The cache is not migrated**: pnpm's `.pnpm-store` is skipped (rebuildable, and possibly several GB), which the dialog states.
  - **A migration is refused while any profile is running**, so live executables and homes are never copied out from under a process.
- **Profiles are out of scope**: they stay at `<dsh home>/profiles`, which is the host's own contract (a directly launched `dsh` reads the same place); the launcher does not move them. The panel says so, and says that the settings database and the logs stay under `userData` too.
- **Leftovers are surfaced**: if you had pointed the plugin store or the version repo somewhere specific before, the panel shows that data is still sitting there — it never deletes it for you.

#### ✨ Features · UI

- **The Profile and Run pages each remember their DSH.** Switching tabs unmounts the whole section, so the choice reset to the first registered dsh on every visit — and on every restart. Both pages now remember their own, kept beside the theme and the plugin filters, and **independently**: the dsh you browse profiles in is not necessarily the one you launch from.
  - A remembered dsh that has since been removed falls back to the first registered one; no cleanup needed.
- **The Run page's DSH selector moved into the rail's header**, matching the Profile page, so the launch target is switchable without scrolling back to the top of the content.

#### 🐛 Fixes

- **Every official bundle was reported missing on a pnpm install.** Bundle resolution was a `node_modules root + package name` join, but pnpm links only **direct** dependencies into `node_modules/@deepseek-ai/` — that directory holds just `dsh`, and every other official bundle is a **transitive dependency** of it, sitting in `.pnpm/<pkg>@<ver>_<hash>/node_modules`. The consequences were:
  - validation called a healthy profile broken and unlaunchable;
  - the plugin list and layer stack **silently skipped** those layers (zero composed rows);
  - worst of all, **"reconcile" deleted them from the profile's `dsh.profile.bundles`**, since the test was "resolves nowhere = not installed".
  - Resolution now goes through the dsh install itself: along Node's lookup chain, anchored at the **real path** (a symlink/junction path is on no lookup chain at all). All four official bundles resolve.
- **Retrying a DSH version-repo migration skipped the home directories.** The repo and the `homes/` beside it are inseparable (a home is always `<dirname(versionDir)>/homes/<name>`), but the completion check looked only at the repo. After an attempt where the repo copied and a home failed, the retry considered the item done and skipped it — leaving every dsh's home pointing at a directory that never arrives. Completion now covers the repo **and** each instance's home.
- **One dead link failed an entire migration.** The copy dereferences, so a junction whose target is gone — which an install upgrade leaves behind — threw `ENOENT`. Such entries are now skipped: there is no content behind them to lose, and they must not block the move.

#### ⚡ Performance

- **A profile's search roots are built once per composition pass.** Building them walks up to the install anchor and compiles a Node lookup chain, and every bundle in a composition rebuilt it; through the profile list that multiplies into `profiles × bundles` synchronous filesystem calls. It is now built once and passed down, with single-bundle callers unaffected.

#### 🏗️ Engineering / architecture

- **Disk resolution extracted into `core/store/module-resolve.ts`**, shared by `combo.ts` and `module-index.ts`. The two had separate "where is this package" implementations and only one understood the pnpm layout — which is exactly how the bug above survived. They now share one chain, without a cycle (`module-index.ts` already imports the plugin list from `combo.ts`).
- **The two bundle judgements are now separate and documented**: "has a patch file" and "declares a patch" are different questions, and the second is the sole basis on which reconcile deletes a layer.
- Removed the `dsh:setVersionDir` and `plugins:setDir` channels plus `setVersionDirValue`: the data root is the single write path for those three directories, and the install dialog's per-run location no longer writes itself back into settings.
- **Tests went from 794 in 64 files to 829 in 67**, including regressions for the pnpm layout, dangling links, and the half-moved state — the last had no coverage at all, which is what let the retry defect through.
- No new runtime dependencies.

# DSH Launcher v0.5.0-beta1

> 本版主线是**让 preset 真的能用**：新增一级「预设」标签页，同时服务 dsh 先后两套 preset 模型（目录模型，以及 0.2.0-rc.1 起的声明模型），并按 profile 给出「能不能用」的评级。围绕它落地的是 0.2.0-rc.1 的一整串连带修复 —— `dsh.bundle.patch` 的数组形式此前只被读成第一个文件，一个健康的 profile 会因此被报出幻影冲突。此外**注册表可配置**、开发插件快照改走 `pnpm pack`、profile 引用的第三种状态变得可见，技能页换上与预设页一致的「打开」菜单。**本版含一处兼容性护栏变更**（设置 schema 2 → 3）。

### 中文版

#### ⚠️ 兼容性

- **设置 schema 从 2 升到 3**，新增可选字段 `registryUrl`。纯增量、没有数据搬移步骤，但护栏与上一版同源：**本版导出的 `settings.json` 会被旧版本拒绝导入**（有意的保护），而不是静默丢掉其中的注册表设置。
- **降级会丢注册表设置**：回到 ≤ 0.4.0-beta2 后，旧版的白名单不认识 `registryUrl`，**任何一次设置写入都会把它清除**。这个值可以重建（就是一个 URL），但如果你在用私有镜像，**先把它记下来**。
- 升级方向不受影响：本版正常读取旧版本的设置与导出文件。

#### ✨ 新功能 · 预设页

- **新增一级「预设」标签页**，管**一个 profile** 的 agent preset：名册、四项元数据（id、名称、描述、优先级）、它定义在哪个文件里，以及它在这个 profile 下能不能用。页面右上角选 profile —— 声明模型的名册本来就是 per-profile 的事实：同一个 dsh 的两个 profile 可以选中不同的 bundle 版本，一个 profile 补丁里的声明在另一个里并不存在。
- **同时服务两套模型，不问你正在看哪一套**：
  - **目录模型**（dsh ≤ `0.1.5-rc.2`）：preset 是一个目录，元数据在 `preset.yml`，从内置包与 `<home>/.agent-presets` 两个根按 dsh 自己的优先级发现。
  - **声明模型**（`0.2.0-rc.1` 起）：preset 是补丁层里的一行普通插件，元数据在 `config.name` / `config.description` / `config.order`，插件名册在 `config.plugins`。
  - **判定看组合里挂了谁，不看版本号**：版本号说的是**装了什么**，组合里挂着谁说的是**跑什么** —— profile 仍选中旧版 bundle、或新版装了没被组合进去时，两者不一致。所以判定按 profile 做，而不是按 dsh 做。
- **评级是「这个 profile 能不能用」**，三值：**可用** / **缺 N 行**（悬浮点名像 `row "id": 包名` 的每一行）/ **不可用**（组合读不出来，带原因）。它走的解析链比 host 自己的健康检查更宽 —— host 只从安装链向上走、判的是名册，两者不一致的地方正是这个评级要回答的，比如某个插件只装进了某一个 profile。`!!js` 的 `name` 不判定，计入「由运行时决定」：宁可少报，也不把一个 loader 能接受的 preset 判死。
- **每行两个控件**：「打开」下拉（在文件管理器中显示 / 用 VS Code），和一个「…」菜单（编辑描述 / 复制 / 删除）。只读的 preset 因此只是少一个菜单项，而不是一个要自己解释自己的禁用按钮。
- **只写当前 profile 的补丁层**：bundle 层属于部署（`preset.readOnly`），home 层（`<home>/cordis.patch.yml`）是用户自己的、但**机器级、所有 profile 都组合它**（`preset.homeReadOnly`，行上给的原因也不同）。分成两个码是因为文案由 code 决定 —— 一个码只可能说出其中一种原因，而「内置不能改」与「改了会影响所有 profile」是两件事、两个改法。只读不等于不可读：**复制仍允许以 home 层声明为源**（副本落在 profile 层）。
- **新建**两种起点，同一个弹窗里切换：以内置的极简模式为起点，或从名册里任选一个复制。**「已占用」的名册来自名册 + 退役目录** —— core 两样都拒（退役目录的 id 一旦迁移就会撞），而名册只显示前者，所以只按名册判就会给出一个必然失败的「创建」。
- **描述**：`0.2.0-rc.1` 的四个内置 preset 在数据里**没有** `name` 和 `description`（`config` 只有 `id` 和 `order`），所以它们的卡片标题退回 id、简介是「（没有描述）」。**这是数据属性，不是缺陷** —— 宿主的 schema 支持这两个字段，只是官方没填；launcher 不替它编文案（内置文案会随官方措辞变更而陈旧）。想要一个有描述的 preset，正路是**复制一份再改**。
- **旧目录迁移**：在声明模型的 dsh 上，`.agent-presets` 里剩下的目录会被标为**不会被加载**，并可一键「迁移为声明」（id 取目录名，name/description/order 取 `preset.yml`，`plugins` 取 `agent.cordis.yml` 逐字）。**旧目录一个字节都不动**；已有同 id 声明的目录标为「已有同 id 的声明」，按钮不可用。
- **两处写入不许重新渲染组合文本**：声明行的 `config.plugins` 里可能有 `!!js` 门与 `|` 块标量 —— `!!js` 只能以私有哨兵存活、**绝不能进 dump** —— 所以改描述只动三个标量行、复制是整段文本切片后改缩进，其余字节一律不动。新建行的 loader id 刻意用 `local-preset-<id>` 而不是官方的 `preset-<id>`：**loader 行 id 撞了会让 dsh 拒绝启动整个 profile**，而 preset id 撞了只让那一条声明失败，所以撞车退化成「一个坏行」而不是「起不来」。

#### ✨ 新功能 · 注册表

- **注册表可配置**：`registryUrl` 一个设置，由「选哪个版本」与「取包」两处共用。此前这两处是仓里仅有的硬编码 npm URL，都写死 `registry.npmjs.org`，而 pnpm 读用户的 `.npmrc` —— 这破坏了唯一重要的那条不变量：**选版本与取包必须问同一个注册表**。两个后果都可见：内网环境**根本装不上**（`latest` 的解析发生在 spawn pnpm 之前，所以查版本这一步就抛了，哪怕每个包都已在镜像里）；镜像的 `latest` 与公网不一致时会**装上用户没要的版本**。
- 配置值**会被校验而不是被信任**（它经文本框与设置导入到达）：不可用时报警告并回退公网 —— 静默按 `file:` scheme 取包更糟，而静默拿公网顶替用户要的镜像，正是这个设置要终结的那种困惑。dsh 的安装与更新检查无需第二个开关就继承了这条修复。
- pnpm 侧的接线（`runPnpm` 的 project split）是下一步；在此之前，未设置的行为与之前逐字相同。

#### ✨ 新功能 · 插件与开发快照

- **开发插件快照改走 `pnpm pack`**。开发插件活在 pnpm monorepo 里，清单写着只有那个 monorepo 能解析的协议；从外面加进 store，暂存项目会以 `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND` 失败、**什么都归档不了**。`pnpm pack` 正是 `npm publish` 已经做的那次改写（`workspace:*` → `3.2.1`、`workspace:^` → `^3.2.1`、`catalog:` → `^4.1.0`），并且尊重 `files` 白名单、跑 `prepack` 脚本（快照因此拿到一次新的构建）。唯一前提是 monorepo 装过 —— 没装时以 `needsInstall` 报出，而不是一墙 pnpm 输出。
- 快照**原地替换已归档的同号版本**（源树动了、版本号没动，此前会静默保留先前状态却报成功），并能在同一次运行里把 profile 从 `link:` 切到归档（毕业此前是两步手工操作，互相覆盖依赖项）。切换失败时旧归档会**被放回**，所以归档从不因为一次重建失败而不存在。
- 缺失的 peer **不算**问题：host-service peer 由 profile 在运行时供给，而在归档里带一份私有的它恰恰是这条路存在要防的事。这些以提示报出，让「没有它」读起来是有意的。
- **删除仍被 profile 引用的版本改为拒绝**，点名列出的 profile，并把拒绝变成建议（「先解绑那些，再删」）。删除是库侧动作、解绑是 profile 侧动作，只做前一个正是那个 bug。「解绑」也成了一等的行操作 —— 这个操作的单位本来就是 (dsh, profile) 对；开发插件页也得到「attach to profile」的镜像。
- **profile 对一个插件有三种状态，第三种此前不可见**：`none`（没声明也没装）/ `ok`（装了且读得回来）/ **BROKEN（声明了，却指向一个已不存在的东西）**。BROKEN 由日常操作到达：删除一个归档版本从不曾解开指向它的 profile，于是 profile 留着一条指向已消失目录的 `file:` —— 而 `existsSync` 把断链读作「不存在」，恰好与「从没装过」长得一模一样。现在按**声明的 spec** 判定（那是这个状态唯一可见的地方），显示与拒绝共用同一个判据 —— 否则界面会提供一个后端随后拒绝的修复。

#### ✨ 新功能 · 技能页

- **技能不再有文本框编辑**。技能是一个**目录**（`SKILL.md` 旁边还有 scripts、references、assets），文本框只可能装下其中一部分，而值得看的副本通常正是启动器不能改的那些。每张技能卡现在给的是预设页给 preset 的那件事：**显示文件夹，或交给编辑器** —— 每一份副本都有，不只可写的那份。交给编辑器的是技能本身：bundle 交给它的**文件夹**（作为工作区打开，资源文件都在树里），而扁平 `<name>.md` 仍作为文件打开（它的文件夹就是整个根）。新建只写启动器自己的脚手架并**拒绝覆盖**任何东西，IPC 契约在两处都收成 create / open / delete。
- **dsh 技能页重做**：技能从「分隔线之间的行 + 一块 96px 虚线拖放区」变成**卡片网格**（一个技能一个单位、自带它的操作），扫描到的根**上移为一块安静的区块**（长路径保持单行、全文在悬浮与复制里），导入手势**归面板自己**（一个只在拖拽期间存在的覆盖层，与技能库页共用同一个组件），首次读取显示**形状一致的骨架**而不是先空后填，切换 dsh 不再留着上一台的卡片。
- 顺带修掉两处读起来不对的标签：来源标签不再说 Personal（改为 This dsh / Machine agents），而一个由 preset 贡献的根**只戴一个标签**、点名带它来的那个 preset —— 它此前戴着泛泛的「From a preset」又戴着「From preset cordis」，一个根读起来像两个。
- **列出 preset 贡献的技能根**。preset 确实带技能，但从不作为自己的字段（`@deepseek-ai/dsh-agent-preset` 的 schema 是 `{id, name, description, order, plugins}`，没有别的），它通过每个组合都在用的 `skill-filesystem` 行挂载。此前只读 home 层，于是内置 cordis preset 自己的两个技能**在每一台机器上都挂着、却从不显示**（实测：改前 3 个技能全是 `user-dsh`，改后同一台是 5 个）。

#### 🐛 修复 · dsh 0.2.0-rc.1 兼容

- **一个组合包声明的多个 patch 文件此前只读了第一个**。`dsh.bundle.patch` 接受一个文件或一个有序列表，而 `0.2.0-rc.1` 的 `dsh-web-app` 用的正是列表形式（`cordis.patch.yml` + 四个 `presets/*.patch.yml`）。只认字符串形式，于是那四个文件**全部不可见**：没有错误，只是一个空的预设名册、以及缺了整块 entry 的组合视图。
- **子包扫描把数组交给 `path.join`**，从 `install` / `uninstall` / 已装概览的调用方抛出 `TypeError`。现在这个声明有唯一读取处，两个消费者不可能再对「这个组合包装了哪些文件」有不同答案。
- **层 = 组合包，文件是层内的维度**。一个声明了 5 个 patch 文件的 bundle 此前被列成 5 层 —— 同一个名字出现 5 次、编号成 5 个独立层，而卡片的 React key 只由包名派生，所以那 5 个还相撞。宿主的单位就是组合包（`profile.layers` 每项带一个 `patchPaths` **列表**），而能启用 / 停用 / 移除的也只有组合包。
- **只有 patch 结构里的 entry 才算「一行」**，行自己的 `config` 是插件私有数据。按文件缩进读会把一个声明里的整套插件名册当成该层 insert 的 entry，于是**一个启动正常的 profile 被报出 32 条幻影「重复插入的 entry id」**、名册里多出幻影插件、删除确认里的补丁行数从 2 变成 40。写侧同理：按 id 改会命中名册里的 `tool-bash`，把 preset 的私有数据改掉。
- **一处声明里的 `disabled` 被读成整行的 `disabled`**：缩进盲的扫描在 `config` 内部的第一个匹配处就结束了，而 `config.plugins` 里的插件行自带 `disabled`（官方 `standard` preset 就 disable 了好几个）—— 于是声明被读成 `disabled: true`，整条从名册里消失。
- **CRLF 的补丁文件会整份丢掉声明名册**：`(.*)$` 在 JavaScript 里不匹配回车、`$` 只匹配输入末尾，所以对 CRLF 行是直接失败（而不是多捕获一个字符）—— 而每一处标量读取都是这么写的。同一份 CRLF 文件还会把 `disabled` 的行读成启用的，并让重复插入的预检看不到它的 insert 列表。同批的另一个缺陷：重复 loader 行 id 的判定此前是文本搜索 `- id: <row>\n`，漏掉 CRLF、最后一行没有换行、以及 `- id:  x` 多一个空格，还会命中某个声明的 `config.plugins` 里的插件行（那不是 loader entry、不可能撞）。**这两条都让 dsh 拒绝启动整个 profile**，而 launcher 当时正在往里追加第二行同 id 的声明。

#### 🐛 修复 · store 与路径

- **导入一个名为 `...zip` 的文件会删掉整个 store**。提取目录由所选 zip 的文件名派生（去掉 `.zip` 后缀），`...zip` 剥完就是 `..`，而 `join(storeDir, '.import', '..')` 正是 store 本身 —— 随后的递归删除清掉了每一个已归档插件、每一个打包好的 tarball 与来源记录。现在任何**全点号**的段一律拒绝（全点号的名字永远指向一个已存在的祖先），且 zip 派生的那一段是在后缀剥掉之后才检查的。
- **包自己声明的版本号此前没被检查**，而它决定了 `archive/<name>/<version>/` 与替换时用的 `.trash` 叶子名。registry 来源由 registry 保证 semver，但 `github:` 或本地 zip / 文件夹来源自己声明 —— 一个写着 `..` 的包会把两条路径都建到 store 外面，而在替换路径下，那意味着把一个目录改名到一边、再递归删除它。开发包名也在**清空 `<store>/.pack/<name>` 之前**过护栏（`../../x` 曾把一次递归删除指向用户从未指定的目录）。
- **每个版本的 tarball 此前按包存，而打包会先清空那个目录**。归档把自己的 tarball 依赖记成 `file:` spec，所以修复或重建一个已归档版本要重新解析那条路径 —— 一次版本号变更就删掉了上一个归档仍指向的 tarball，让那个版本**永久装不回来**。
- **profile 清单在安装失败后不再留下半句话**：此前先写依赖、再做让依赖成真的安装，且没有退路 —— 安装失败就留下一条指向不存在包的依赖，profile 从此装不干净，而下一次失败什么都不说。现在它保留起始的清单文本，任何在首次写入之后发生的失败（包括最后那步 bundle 层追加）都逐字写回。
- **路径比较改用平台语义**，不再用字符串前缀。删除一个已归档版本前要先问哪些 profile 还指着它，而这个答案决定删除是否发生；两种拼写来自不同时刻（spec 来自清单写下的那一刻，路径来自现在的设置），在 Windows 上可能大小写不同却指向同一个目录 —— 前缀判定答「没人引用」，于是版本被删、profile 留下一条指向已消失目录的 `file:`，一个 UI 无法与「从没装过」区分的悬空引用。同一个比较用作包含判定时，还会把根内的路径误判为根外。
- **暂存项目先写自己的 pnpm workspace**。此前归档一个版本是在一个只有 `package.json` 的暂存项目里跑 `pnpm add`，于是 pnpm 用它自己的默认值，而两个默认值对插件归档都是错的：`autoInstallPeers` 会从**注册表**解析该包的 host-service peer（`@deepseek-ai/dsh-*`、cordis）—— 实测一个两个 peer 的插件拖进 **49 个包**、把整个 host 栈钉死，归档于是带着一份从它自己的树解析出来的私有副本，host 一动就过时；`nodeLinker: isolated` 把聚合包的子包藏进 `.pnpm/`（同一个聚合包裸装是 1 个顶层条目、带提升工作区是 **87 个** —— 移植后那次重命名的提升就是为此存在）。没有自己 workspace 的项目还可能**静默认领一个祖先 pnpm workspace** 并装到那里去。

#### 🐛 修复 · 判定与错误码

- **`versions[0]` 不再被当作「最新」**。四个调用点这么读，而那个数组是注册表版本映射的 `Object.keys()`，顺序是注册表自己的（npm 按发布顺序返回，最旧的在前）。实测 `left-pad`：index 0 是 `0.0.3`，而 `dist-tags.latest` 是 `1.3.0`。四个之一让「安装最新」装上最旧的版本，另一个把最旧版本与已装版本相比，于是**静默停止提供任何更新**。现在 `latest` 标签优先（且必须真的是列表里的一个版本 —— 一个不在选项里的预选值会渲染成空白下拉），没有可用标签时取**语义最高的**而不是数组的任一端（镜像并不保证有序）。
- **八个错误码在中英两种语言里都没有文案**，于是拒绝以裸参数或原始 code 到达用户；另有一个码以两个不同的参数名调用，会渲染出字面占位符。全部补齐，并加了一条**遍历整个目录**的测试：新增一个码而没写文案会在 CI 失败，而不是在用户机器的 toast 上才出现。
- **升级缓存把注册表纳入键**。「最新」来自某个 host，所以切到私有镜像后每一行的答案都变了，而上一个 host 的判定在整个 TTL 内继续被当成答案 —— 错的方向恰好读作「没有更新」。
- **被拒绝的注册表 URL 此前返回「名称无效」**：文案按 code 查、优先于原文，于是唯一有用的那部分（哪个 URL 被拒）被丢掉了。现在有专用码，URL 作为参数被文案插值。
- **切换 dsh 后拿上一台的名字去问当前这台**，主进程以 `profile.notFound` 正确拒绝（静默丢弃一个 profile 会读作「这台 dsh 什么都没有」），代价是每次切换一次错误 toast 与一次白跑的列表 —— 在一次真实会话的日志里出现了**八次**。名字现在带着它的来处（读自哪台 dsh），未被读过的 scope 答 `undefined`，被拒的名字重读一次再问，而不是把这次拒绝报给用户。
- **控制台那一行把自己的原因藏起来了**：控制台 sink 只打印消息、丢掉其余元数据，于是 IPC 边界的失败行读作 `ipc fail: ext:skillList`，原因只在文件的 JSON 里 —— 那一天有八条这样的行，而人只会 grep 那一行。现在顶层 code 会附在消息后面。

#### 🐛 修复 · 技能

- **一个读不出来的条目不再让整个页面失败**。技能库页在做事之前先扫目录，而那次扫描对每个条目都是无护栏读取：一个 `SKILL.md` 是目录（或因为任何别的原因读不出来）的条目会从事 `listSkillLibrary` 抛出来，两条库路由全失败、页面**什么都渲染不出来**。同类问题在按 dsh 扫描与技能目录扫描上各有一处，而后者才是最初的抛出点：**一个**半删掉的副本、一次权限变更或一个畸形条目，会隐藏**所有 dsh 上的所有其他技能**。现在不能读的条目是一个 ISSUE（带路径与错误），相邻条目保留各自的判定。
- **一个不能读的副本此前看起来像一个需要重装的副本** —— 而那正是唯一修不好它的动作。原因键的判定收在一处（problem 压过 installed 与 stale），三个界面共用；降级的一格报 `stale` 而不是 current，因为「我们说不准」与「它是最新的」是两个答案，而只有后者支持放着不管。
- **技能列表失败不再谎称「这台 dsh 还没有技能」**：面板此前只有 loading 与 empty 两态，一个被拒或失败的读取会落进空状态 —— 那是一个用从未回答的读取对用户的 dsh 下的断言。失败现在有自己的状态（原因进 alert，网格与空状态让开，成功加载会清掉它，切换 dsh 时随列表一起丢弃）。
- **`!!js` 表达式不再被当成技能根解析**。`!!js` 标量在 js-yaml 里以哨兵前缀的字符串存活，所以 `typeof v === 'string'` 的过滤留下了它、并把它当路径解析。实测于一个装着官方 cordis preset 自己那条表达式的临时 home：得到一条**带 NUL 字节、含 JavaScript 源码、按进程 cwd 解析**的路径（还顺手把表达式里的斜杠规范化了）。官方 preset 写的正是这种形式，所以这是常见情形而非边界情形。运行时根现在如实报出（`runtime: true`、`path` 存原表达式、`exists` 强制 false 因而永不被探测），两个事实在构造处**被强制绑在一起**而不是互相推导，将来的调用方造不出一个「声称存在」的运行时根。
- **空值与纯空格的技能根视为未配置**。四个路径字段此前用两套标准读：`customSkillDirs` 知道 `!!js` 会解析成哨兵前缀字符串并拒绝解析它，而 `dshHome` / `agentsHome` / `bundledSkillDir` 只检查「是不是字符串」，于是哨兵直接进了 `resolve()`。`dshHome` 是三个里最糟的，因为它**替换**真正的可写根：`user-dsh` 根从列表里消失，一个什么都写不进去的根被报成可写。空值在两侧都重要：`resolve('')` 是进程工作目录且它确实存在，于是一个空覆盖会让扫描走进启动器自己的 cwd，把它在那里找到的随便哪个 `SKILL.md` 报成这台 dsh 的技能。

#### ⚡ 优化

- **打开一个 preset 不再为了一行路径把整份名册逐行走一遍解析链**（每行一次模块解析、无缓存），每次写入也不再组合两三次层叠栈：定位只定位，每次写入只组合一次。
- **归档版本的重新链接变便宜了**：刚构建的版本只需要一次 `pnpm install`，因为它要的东西已经都在这次调用用过的 store 里。此前每次新归档都要付两次联网重试的 offline / online / force 阶梯，而那条阶梯本来是**修复**路径 —— 现在只在单次重链之后仍读不出可用的包体时才跑。
- **dev 包重命名后的那次聚合检测连同它一起消失**，因为 workspace 是在 add 之前就写好的，归档在第一次构建时形状就是对的。

#### 🏗️ 工程 / 架构

- **`dsh.bundle.patch` 有了唯一读取处**（`core/store/bundle-manifest.ts`）。此前有两个各自复刻的版本，于是数组形式各错一种：组合层读取只认字符串形式（名册全空、不报错），子包扫描把数组交给 `path.join`。
- **「一行 entry」的判定收敛为一处**：`patch.ts` 的 `positionedRows` 是全部读取器（`parseNamedRows` / `parseClassifiedRows` / `collectInsertIds` / `findIdLine`）唯一的定义，走的是 host `applyEntryPatches` 的结构而不是文件的缩进 —— 两套口径正好在要紧的地方分歧，所以只能有一套。与启动预检同源之后，「这个 id 被占用了吗」在全仓只有一个答案。
- **错误码目录移到 `src/shared/error-codes.ts`**：`tsconfig.web.json` 不允许 renderer 从 `src/main` 导入，而错误码本来就要跨进程（renderer 把 code 变成一句话），共享区才是它该在的地方；主进程侧模块重新导出，现有导入没有迁移，那条「每个码都要有文案」的测试也才有地方存在。
- **`pathWithin` 成为路径包含判定的单一原语**（构建在 `path.relative` 上），`pathOutsideRoot` 是它的取反，所以两个方向不会各自漂移。
- **视图测试有了入口**：`react-dom/server` 静态渲染 —— 不需要 DOM、不新增依赖、覆盖率仍然只算 core。三条边界写进了 `docs/TESTING.md`（Modal 经 portal 渲染、tooltip 悬浮才渲染、effect 不运行），并借此关掉了早先两批留下的两个验证缺口。
- **文档拆成三线**：`docs/README.md` 写明规则 —— `specs/` 放「现在必须怎样」的契约，`design/` 放尚未落地的方案，`releases/` 带日期且永不改写，根文件是流程与手册。2026-08 的代码审计报告被删除（它的结论已全部落地，剩下的只是过时的路径与行号），旧设计稿里已成为行为的部分上收为契约（profile / launch / extensions），两个仍值得留的计划作为设计保留（assembly / egress）。**27 条缺陷修复计划也按同一条规则删除** —— 每条都已修完或已确证不必改，规则按性质上收进 `specs/profile.md`、`specs/extensions.md`、`presets.md`、`ui-guidelines.md` 与 `TESTING.md`，计划本身连同各批账目留在历史里。
- **测试从 829 项 / 67 文件增至 1150 项 / 93 文件**（1149 通过 + 1 跳过），新增了针对两套 preset 模型的读写与折叠、数组形式 `dsh.bundle.patch`、CRLF 补丁、路径段护栏、开发快照编排、降级单元格，以及视图渲染的用例。

### English

> This release is about **making presets actually usable**: a new top-level Presets tab that serves both agent-preset models dsh has shipped (the directory model, and the declaration model from 0.2.0-rc.1) and grades each preset against one profile. It lands with the whole chain of 0.2.0-rc.1 fallout — the array form of `dsh.bundle.patch` was only ever read as its first file, which made a healthy profile report phantom conflicts. Alongside it: a **configurable registry**, dev-plugin snapshots through `pnpm pack`, a third profile-reference state made visible, and the skills page given the same Open menu the presets page has. **One compatibility guard changes** (settings schema 2 → 3).

#### ⚠️ Compatibility

- **The settings schema goes from 2 to 3**, adding the optional `registryUrl` field. Purely additive with no data-shape step, but the guard is the same one as last time: **a `settings.json` exported by this version is refused by an older one** (a deliberate guard) rather than silently dropping the registry setting from it.
- **Downgrading loses the registry setting**: back on ≤ 0.4.0-beta2, the older whitelist does not know `registryUrl` and **any settings write clears it**. The value is reconstructible (it is one URL), but if you are on a private mirror, **note it down first**.
- Upgrading is unaffected: this version reads older settings and older exports normally.

#### ✨ Features · The Presets page

- **A new top-level Presets tab** managing **one profile's** agent presets: the roster, the four fields the launcher owns (id, name, description, priority), where each one is defined, and whether it is usable under that profile. The profile selector sits in the page header — a declarative roster is a per-profile fact, since two profiles of one dsh may select different bundle versions and a declaration in one profile's patch layer does not exist in another's.
- **It serves both models without asking which one you are looking at**:
  - **Directory model** (dsh ≤ `0.1.5-rc.2`): a preset is a directory, its metadata is `preset.yml`, and it is discovered from two roots in the host's own precedence order — the built-in package, then `<home>/.agent-presets`.
  - **Declaration model** (from `0.2.0-rc.1`): a preset is an ordinary row in a patch layer, its metadata is `config.name` / `config.description` / `config.order`, and its plugin roster is `config.plugins`.
  - **The model is read off the composition, never off a version number**: a version says what was *installed*, the composition says what *runs*, and the two differ whenever a profile still selects an older bundle or a newer one is installed without being composed in. The answer is therefore per profile, not per dsh.
- **The grade answers "can this profile use it"**, three-valued: **usable** / **N rows missing** (the hover names every row, as `row "id": package`) / **unusable** (the composition cannot be read, with the reason). It walks a wider resolution chain than the host's own health check — the host walks the install chain alone and judges a roster — and the places where the two disagree are exactly what the grade is for, such as a plugin installed into one profile only. A `!!js` `name` stays undecided rather than counted as missing: under-reporting beats calling a preset the loader accepts broken.
- **Two controls per row**: an Open dropdown (show in the file manager / open in VS Code) and a "…" menu (edit description / copy / delete). A read-only preset therefore simply has one menu entry fewer, instead of a disabled button explaining itself.
- **Writes go to the current profile's patch layer only**: a bundle layer belongs to the deployment (`preset.readOnly`), and the home layer (`<home>/cordis.patch.yml`) is the user's own but **machine-level, composed by every profile** (`preset.homeReadOnly`, with a different reason on the row). Two codes because the sentence is chosen by code — one code can only state one of the causes, and "built in, cannot change" and "changing it affects every profile" are two causes with two different remedies. Read-only is not unreadable: **a home-layer declaration is still allowed as the source of a copy**, which lands in the profile layer.
- **Creating** offers two starting points in one dialog: the deployment's own minimal preset, or a copy of any preset on the roster. **The "id in use" set is the roster plus the retired directory** — the core refuses both (a retired directory's id collides the moment it is migrated) while the roster shows only the first, so judging by the roster alone would offer a Create button that is certain to fail.
- **Descriptions**: the four built-in presets of `0.2.0-rc.1` carry **no** `name` and **no** `description` in their data (`config` holds only `id` and `order`), so their cards fall back to the id as a title and to a "(no description)" placeholder. **This is a property of the data, not a broken read** — the host schema accepts both fields and the official declarations simply omit them; the launcher does not invent copy for them, since built-in text would go stale as the official wording changes. The one road to a described preset is to **copy one and edit the copy**.
- **Legacy directory migration**: on a declaration-model dsh, the directories still sitting in `.agent-presets` are reported as **not loaded** and can be migrated to a declaration in one click (id from the directory name, name/description/order from `preset.yml`, `plugins` from `agent.cordis.yml` verbatim). **The old directory is left byte-for-byte untouched**; a directory whose id is already declared says so, and its button is disabled.
- **Two writes must never re-render composition text**: a declaration's `config.plugins` may hold `!!js` gates and `|` block scalars — a `!!js` value survives only as a private sentinel and **must never be dumped** — so editing the description touches three scalar lines only, and a copy is a text slice of the block re-indented, with every other byte preserved. A newly created row deliberately uses `local-preset-<id>` rather than the shipped `preset-<id>` convention: **a repeated loader row id makes dsh refuse to boot the whole profile**, while a repeated preset id fails only that one declaration, so a collision degrades into "one broken row" instead of "it does not start".

#### ✨ Features · Registry

- **The registry is configurable**: one `registryUrl` setting, shared by "which version" and "fetch the package". These were the only two hardcoded npm URLs in the repo, both saying `registry.npmjs.org` while pnpm read the user's `.npmrc` — which broke the one invariant that matters: **choosing a version and fetching the package must ask the same registry**. Both consequences are visible: an air-gapped install **cannot start at all** (resolving `latest` happens before pnpm is ever spawned, so the version lookup throws even with every package mirrored), and a mirror whose `latest` disagrees with the public one installs a version the user did not ask for.
- The configured value **is validated rather than trusted** (it arrives through a text field and a settings import): an unusable one warns and falls back to the public registry, because silently fetching from a `file:` scheme is worse, and quietly substituting the public host for a mirror a user asked for is exactly the confusion this setting exists to end. The dsh install and update checks inherit the fix without a second knob.
- Wiring pnpm to the same value is the `runPnpm` project split, which comes next; until then an unset value behaves exactly as before.

#### ✨ Features · Plugins and dev snapshots

- **Dev-plugin snapshots go through `pnpm pack`.** A dev plugin is developed inside a pnpm monorepo, so its manifest speaks protocols only that monorepo can resolve; added from outside it, the store's staging project failed with `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND` and **nothing was archived at all**. `pnpm pack` is the rewrite `npm publish` already performs (`workspace:*` → `3.2.1`, `workspace:^` → `^3.2.1`, `catalog:` → `^4.1.0`), it honours the `files` allowlist, and its `prepack` scripts run — which is how a snapshot gets a fresh build. The one precondition is that the monorepo is installed, and that is surfaced as `needsInstall` rather than as a wall of pnpm output.
- A snapshot now **replaces the archived version in place** (the source tree moved on, the version did not — the call used to report success while keeping the previous state) and can switch profiles off their `link:` onto the archive in the same run (graduating used to be two manual steps that overwrote each other's dependency entry). A failed switch **puts the old archive back**, so an archive is never absent because a rebuild broke.
- A missing peer is **not** a problem: host-service peers are supplied by the profile at run time, and carrying a private copy of them in the archive is the thing this path exists to prevent. Those are reported as notes, so the absence reads as deliberate.
- **Deleting a version a profile still points at is now refused**, naming those profiles and turning the refusal into an offer ("detach those and delete"). Deleting is a library-side act and detaching is a profile-side one; doing only the first is the bug. Detach is also a first-class row action now — the unit of the operation is a (dsh, profile) pair — and the dev-plugin page gets the mirror of "attach to profile".
- **A profile has three states with respect to a plugin, and the third used to be invisible**: `none` (nothing declared, nothing installed) / `ok` (installed and reads back) / **BROKEN (declared and pointing at nothing)**. BROKEN is reached by ordinary use: deleting an archived version never detached the profiles pointing at it, so a profile kept a `file:` aimed at a directory that no longer existed — and `existsSync` reads a dangling link as absent, which is exactly what a profile that never installed anything looks like. The state is now read off the **declared spec** (the only place it is visible), and the display and the delete guard share one predicate — otherwise the UI would offer a fix the backend then refuses.

#### ✨ Features · Skills page

- **A skill has no text box any more.** A skill is a **directory** (a `SKILL.md` beside scripts, references and assets), so a text box could only ever hold part of one, and the copies worth looking at are usually the ones the launcher may not touch. Every skill card now offers what the presets page offers for a preset: **show the folder, or hand it to the editor** — on every copy, not only the writable ones. What the editor gets is the skill itself: a bundle hands over its **folder** (opened as a workspace, with the resource files in the tree), while a flat `<name>.md` entry is still opened as the file it is, because its directory is the whole root. Creating writes the launcher's own scaffold and **refuses to overwrite** anything, and both surfaces' IPC contract narrows to create / open / delete.
- **The dsh skills page was reworked**: skills went from rows between dividers plus a 96px dashed drop block to a **card grid** (one skill, one unit carrying its own actions), the scanned roots moved up into **one quiet block** (long paths stay on a single line, with the full value a hover and a copy away), the import gesture **belongs to the panel itself** (an overlay that exists only while the drag does, shared with the library page through the same component), the first read shows a **skeleton shaped like what is coming** rather than an empty box that then fills in, and switching dsh no longer leaves the previous dsh's cards on screen.
- Two labels that read wrong were fixed with it: source tags no longer say Personal (they read This dsh / Machine agents), and a preset-contributed root wears **one** tag naming the preset that brought it — it used to wear the generic "From a preset" beside "From preset cordis", so one root read as two.
- **The skill roots a preset contributes are listed.** A preset does carry skills, but never as a field of its own (the host schema for `@deepseek-ai/dsh-agent-preset` is `{id, name, description, order, plugins}` and nothing else); it mounts them through the same `skill-filesystem` row every composition uses. Only the home layer was read, so the built-in cordis preset's own two skills **were mounted on every machine and never shown** (measured: three skills, all `user-dsh`, before; five on the same machine after).

#### 🐛 Fixes · dsh 0.2.0-rc.1 compatibility

- **A bundle's multiple patch files were read as the first one only.** `dsh.bundle.patch` accepts one file or an ordered list, and `0.2.0-rc.1`'s `dsh-web-app` uses the list form (`cordis.patch.yml` plus four `presets/*.patch.yml`). Only the string form was read, so all four files were **invisible**: no error, just an empty preset roster and a composition view missing whole entry sets.
- **The sub-bundle scan handed the list to `path.join`**, throwing a `TypeError` out of the `install`, `uninstall` and installed-overview callers. The declaration now has a single reader, so two consumers can no longer disagree about which files a bundle composes.
- **A layer is the bundle; its files are a dimension inside it.** A bundle declaring five patch files was listed as five layers — the same name five times, numbered as five separate layers, with the card React key derived from the bundle name alone so the five also collided. The host's unit is the bundle package, whose `profile.layers` entry carries a `patchPaths` **list**, and the bundle is the only thing a person can enable, disable or remove.
- **Only entries in the patch structure count as rows**; a row's own `config` is plugin-private data. Reading by file indentation treated a declaration's whole plugin roster as entries the layer inserts, so **a healthy profile reported 32 phantom duplicate inserted entry ids**, the roster grew phantom plugins, and the delete confirmation's patch row count went from 2 to 40. Editing by id followed the same mistake, landing on a roster row like `tool-bash` and rewriting a preset's private data.
- **A declaration's own `disabled` was read as the row's `disabled`**: the indent-blind scan stopped at the first match inside `config`, and the plugin rows of `config.plugins` carry `disabled` of their own (the shipped `standard` preset disables several) — so the declaration read as `disabled: true` and vanished from the roster.
- **A CRLF patch file lost its whole declaration roster**: in JavaScript `(.*)$` does not match a carriage return and `$` only matches the end of the input, so a match against a CRLF line fails outright rather than capturing one character too many — and every scalar reader was written that way. The same CRLF file also read a disabled row as active and hid its insert lists from the duplicate pre-flight. A second defect in the same batch: the duplicate-loader-row check was a text search for `- id: <row>\n`, which missed CRLF, a final line without a newline, and `- id:  x` with an extra space, and matched a plugin row inside some declaration's own `config.plugins` (not a loader entry, unable to collide). **Both let dsh refuse to boot the whole profile**, while the launcher was appending a second row with an id already inserted.

#### 🐛 Fixes · Store and paths

- **Importing a file named `...zip` deleted the entire store.** The extract dir is derived from the chosen zip's file name with the `.zip` suffix stripped, `...zip` strips down to `..`, and `join(storeDir, '.import', '..')` is the store itself — which the following recursive removal cleared, taking every archived plugin, every packed tarball and the source records with it. Any **all-dots** segment is now refused (a token made only of dots always names an existing ancestor), and the zip-derived segment is checked after the suffix is stripped.
- **The version a package declares was never checked**, and that value names `archive/<name>/<version>/` and the `.trash` leaf a replacement goes through. A registry source is semver-enforced by the registry, but a `github:` or local zip/folder source declares its own — a package saying `..` built both paths outside the store, and under replace that meant renaming a directory aside and deleting it recursively. The dev package name is guarded too, **before `<store>/.pack/<name>` is cleared** (`../../x` aimed a recursive delete at a directory the user never named).
- **Each version's tarball used to live one directory per package, and packing cleared that directory first.** An archive records its own tarball dependency as a `file:` spec, so repairing or rebuilding an archived version re-resolves through that path — and a version bump deleted the tarball the previous archive still pointed at, leaving that version **permanently unbuildable**.
- **A profile manifest no longer keeps half a sentence after a failed install**: the dependency used to be written before the install that makes it true, with no way back — a failed install left a dependency on a package that is not there, the profile stopped installing cleanly, and the next failure said nothing about why. It now keeps the manifest text it started from and writes it back verbatim whenever anything fails after the first write, including the bundle-layer append at the end.
- **Path comparison now follows platform semantics** instead of a string prefix. Deleting an archived version first asks which profiles still point at it, and that answer decides whether the delete happens; the two spellings come from different times (the spec from whenever the manifest was written, the path from the setting now) and on Windows may name the same directory while differing in case — the prefix test answered "nobody references this", so the version was deleted and the profile kept a `file:` aimed at a directory that no longer existed, a dangling reference the UI cannot tell from a package that was never installed. The same comparison, used as a containment guard, misjudged paths inside a root as outside it.
- **The staging project now writes its own pnpm workspace first.** Archiving a version used to run `pnpm add` in a staging project holding nothing but a `package.json`, so pnpm used its defaults, and both defaults are wrong for a plugin archive: `autoInstallPeers` resolved the package's host-service peers (`@deepseek-ai/dsh-*`, cordis) from the **registry** — a measured two-peer plugin dragged in **49 packages** and pinned the whole host stack, so the archive carried a private copy resolved from its own tree, stale the moment the host moved on; and `nodeLinker: isolated` hid an aggregate bundle's sub-packages behind `.pnpm/` (the same aggregate installed 1 top-level entry bare and **87** with a hoisted workspace, which is why the post-rename hoist existed at all). A project with no workspace of its own can also silently adopt an **ancestor** pnpm workspace and install into that.

#### 🐛 Fixes · Verdicts and error codes

- **`versions[0]` is no longer read as "the newest".** Four call sites read it that way, and the array is `Object.keys()` of the registry's version map, so its order is the registry's own — npm returns them in publish order, oldest first. Measured on `left-pad`: index 0 is `0.0.3` while `dist-tags.latest` is `1.3.0`. One of the four made "install latest" install the oldest release; another compared the oldest version against the installed one and so **silently stopped offering updates at all**. The `latest` tag now wins (and must actually be a version the list carries — a preselected value absent from the options renders as a blank select), and without a usable tag the **semver-highest** wins rather than either end of an array a mirror is not obliged to sort.
- **Eight error codes had no message in either language**, so a refusal reached the user as a bare parameter or a raw code; one code was also called with two different parameter names, which would have rendered a literal placeholder. All of them have one now, plus a test that walks the **whole catalogue**: adding a code without its message fails in CI instead of surfacing in a toast on a user's machine.
- **The update cache now keys on the registry.** "Latest" comes from a host, so switching to a private mirror changed every row's answer while the previous host's verdicts kept being served for the rest of the TTL — wrong in the direction that reads as "no updates".
- **A rejected registry URL used to return "invalid name"**: the message is looked up by code and preferred over the raw text, so the one useful part — which URL was refused — was dropped. It has a dedicated code now, with the value as a parameter the message interpolates.
- **Switching dsh asked the new one about the previous one's profile names**, which the core correctly refused with `profile.notFound` (silently dropping a profile reads as "this dsh contributes nothing"), at the cost of one error toast and one wasted listing per switch — **eight times** in one real session's log. Names now carry the dsh they were read from, a scope not read for this dsh answers `undefined`, and a refused name is re-read once and asked again instead of being reported.
- **The console line hid its own cause**: the console sink prints the message and drops the rest of the metadata, so IPC-boundary failure lines read `ipc fail: ext:skillList` with the reason visible only in the file JSON — eight of them sat in one day's log, and it is the one line a reader greps. A top-level code is appended to the message now.

#### 🐛 Fixes · Skills

- **One unreadable entry no longer fails the whole page.** The library page scans the catalogue before it does anything else, and that scan read every entry unguarded: an entry whose `SKILL.md` is a directory (or unreadable for any other reason) threw out of `listSkillLibrary`, both library routes failed, and the page rendered **nothing at all**. The same class had two more instances, in the per-dsh scan and in the skill-root scan, and the last is where the original throw came from: **one** half-removed copy, a permission change or a malformed entry hid **every other skill on every other dsh**. An entry that cannot be read is an ISSUE now (named with its path and the error), and its readable neighbours keep their verdicts.
- **A copy that cannot be read used to look like a copy that needs reinstalling** — the one action that cannot fix it. The verdict rule lives in one place (a problem outranks installed and stale) and three surfaces use it; a degraded cell reports `stale` rather than current, because "we cannot tell" and "it is current" are different answers, and only the second justifies leaving the copy alone.
- **A failed skill listing no longer claims "no skills on this dsh yet"**: the panel had only loading and empty, so a refused or failed read fell through to the empty state — a claim about the user's dsh made from a read that never answered. The failure has its own state now (the reason lands in an alert, the grid and the empty state stay out of the way, a successful load clears it, and switching dsh drops it with the listing).
- **A `!!js` expression is no longer resolved as a skill root.** A `!!js` scalar survives js-yaml as a sentinel-prefixed string, so the `typeof v === 'string'` filter kept it and resolved it like a path. Measured on a temp home holding the shipped cordis preset's own expression: a path **with a NUL byte, JavaScript source in it, resolved against the process cwd** (with the expression's own slashes normalised on the way). Shipped presets write exactly this form, so it was the common case rather than an edge case. A runtime root is now reported honestly (`runtime: true`, `path` holding the expression verbatim, `exists` forced false so it is never probed), and the two facts are **forced together** where the root is built instead of derived from each other, so no future caller can produce a runtime root that claims to exist.
- **A blank or whitespace-only skill root counts as unconfigured.** The four path fields were read with two different standards: `customSkillDirs` knew a `!!js` value parses to a sentinel-prefixed string and refused to resolve it, while `dshHome` / `agentsHome` / `bundledSkillDir` only checked for a string, so the sentinel went straight into `resolve()`. `dshHome` is the worst of the three because it **replaces** the real writable root: the `user-dsh` root vanished from the list and a root nothing can write was reported as writable. Blank values matter on both sides: `resolve('')` is the process working directory and it exists, so a blank override sent the scan walking the launcher's own cwd and reported whatever `SKILL.md` it found there as this dsh's skills.

#### ⚡ Performance

- **Opening a preset no longer walks the whole roster's resolution chain to produce one path** (a module resolution pass per row, uncached), and a write no longer composes the layer stack two or three times: locating only locates, and each write composes once.
- **Re-linking an archived version got cheap**: a version built a moment ago needs one `pnpm install`, because everything it needs is already in the store that call used. Every new archive used to pay two networked retries on an offline/online/force ladder that is really a **repair** path — it now runs only when a single re-link leaves no readable package body.
- **The post-rename aggregate detection for a dev package went away with it**, because the workspace is written before the add, so the archive has the right shape when it is first built.

#### 🏗️ Engineering / architecture

- **`dsh.bundle.patch` has a single reader** (`core/store/bundle-manifest.ts`). There were two copies of the declaration, and the array form broke each in its own way: the composition reader only accepted the string form (empty roster, no error), and the sub-bundle scan handed the list to `path.join`.
- **"What counts as an entry row" is decided in one place**: `positionedRows` in `patch.ts` is the sole definition used by every reader (`parseNamedRows` / `parseClassifiedRows` / `collectInsertIds` / `findIdLine`), and it follows the host's `applyEntryPatches` structure rather than the file's indentation — the two readings disagree exactly where it matters, so there can only be one. Sharing it with the boot pre-flight also gives "is this id taken" a single answer repo-wide.
- **The error-code catalogue moved to `src/shared/error-codes.ts`**: `tsconfig.web.json` refuses renderer imports from `src/main`, and the codes cross the process boundary anyway (the renderer turns a code into a sentence), so the shared zone is where they belong. The main-side module re-exports them, so no import moved — and the "every code has a message" test has somewhere to live.
- **`pathWithin` is the single containment primitive** (built on `path.relative`), with `pathOutsideRoot` as its negation, so the two directions cannot drift.
- **Views have a test entry point now**: `react-dom/server` static rendering — no DOM, no new dependency, coverage still core-only. Three edges are written down in `docs/TESTING.md` (a Modal renders through a portal, tooltips render on hover, effects do not run), and the two verification gaps left by earlier batches close with it.
- **The docs tree split into three lines**: `docs/README.md` states the rule — `specs/` holds what is true now, `design/` holds what is not implemented yet, `releases/` is dated and never rewritten, and the root files are process and manuals. The 2026-08 code audit report is deleted (every conclusion in it had landed; only its paths and line numbers had gone stale), the parts of the old design drafts that had become behaviour were lifted into contracts (profile / launch / extensions), and the two plans still worth keeping stayed as designs (assembly / egress). **The 27-item defect fix plan was deleted by the same rule** — every item was fixed or proven unnecessary — with its rules lifted by nature into `specs/profile.md`, `specs/extensions.md`, `presets.md`, `ui-guidelines.md` and `TESTING.md`, and the plan itself, with its batch ledgers, left readable in history.
- **Tests went from 829 in 67 files to 1150 in 93** (1149 passed + 1 skipped), adding coverage for reading and writing both preset models, the array form of `dsh.bundle.patch`, CRLF patches, the path-segment guards, the dev-snapshot orchestration, degraded cells, and view rendering.
- **No new runtime dependencies.**
